# Full UI verification

Use this skill only when explicitly invoked. It runs the full StationAI UI suite, diagnoses and repairs failures, confirms the full suite is green, then commits and pushes the changes made by this skill.

## Workflow

1. Read `AGENTS.md`, the verifier instructions in `.codex/agents/`, and the test scripts. Inspect `git status --short` and `git diff` before changing anything. Record pre-existing staged, unstaged, and untracked work so it cannot be swept into the commit.
2. Run `scripts/test-ui-tart.sh` for the full visible UI suite. All UI test execution must happen in the Tart VM, never on the regular host. Require all contract UI cases to execute with no skips, failures, or incomplete results.
3. For each failure, determine whether it reflects a product defect, a test defect, or a behavior that has been intentionally removed. Fix the cause rather than weakening an assertion to make the run green. Before testing each repair, follow step 5 to obtain affected static approvals and required CLI verification. Then use focused `scripts/test-ui-tart.sh --case <case-id>` runs for failed/affected UI cases. Once all repairs pass CLI and focused UI verification, run one final full UI suite in the VM. If the initial full UI suite passes with no repairs, it is final confirmation.
4. If a failing UI test expects a feature or behavior that is absent, inspect read-only Git history (`git log`, `git show`, and related read-only commands) and the surrounding code/docs to determine when and why it was removed. Never restore product code solely to satisfy a failing test. If history clearly shows the removal was intentional, remove the obsolete UI and CLI tests and their shared contract entry, then follow the static-review and CLI verification sequence in step 5. If the history indicates the removal may have been accidental or the intent is unclear, stop before changing product code or deleting tests and ask the user whether to restore the feature or keep it removed. Never bring back the feature without the user's explicit approval.
5. For all product fixes, test updates, or obsolete-test removals, preserve exact CLI/UI case and expectation parity. Follow the two-phase gate in `AGENTS.md` when product behavior, tests, or shared contracts changed: the coordinator starts all applicable static reviewers, resolves their findings, then the main agent runs CLI/XPC verification directly using `.agents/skills/code-review/SKILL.md`. Do not delegate runtime execution or ask the task verifier to dispatch UI reviewers. Apply the non-source-only exemption in AGENTS.md to incidental documentation/configuration edits; explicit full-UI invocation still authorizes the requested UI run. Follow the focused CLI repair guidance after failures. Return to step 3 for focused UI retries and the single final full UI confirmation; do not add a second confirmation run.
6. Before committing, inspect the final unstaged diff and status against the baseline recorded in step 1. Stage only clean-baseline paths changed by this skill, using explicit path arguments to `git add`; then commit with a path-scoped command (for example, `git commit --only -m "..." -- <scoped-paths>`) so unrelated staged entries are not included. If a path the skill needs to commit already had pre-existing staged or unstaged changes at the baseline, do not include that path or disturb its index/worktree state; finish verification and report why the full scoped commit cannot safely proceed. Do not include unrelated work.
7. Push the scoped commit to the current branch's configured upstream. Explicit invocation of this skill is authorization for its path-scoped `git commit` and `git push` operations, as specified in `AGENTS.md`. If there is no configured upstream or the push fails, retain the local commit and report the exact blocker.

## Verification and reporting

Serialize visible UI test sessions through the repository-root `.e2e.lock`; the provided UI scripts acquire it for the full Tart session. CLI/XPC checks and direct app sessions do not use this lock. Report the initial full UI result, each focused repair run, any CLI/parity checks, the final full UI result, changed files, and commit/push outcome. If you pause for the user's decision about a possibly accidental feature removal, state the relevant history evidence and do not commit or push the unresolved change.
