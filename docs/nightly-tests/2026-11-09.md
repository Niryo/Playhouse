## Product changes in this round

These three changes affect product code. The third fixes a click users could hit: New Server stopped
responding after you created an MCP server.

1. **The bridge daemon now starts exactly once when threads of one process race to start it**
   (`Playhouse/Bridge/BridgeSocket.swift`).
   - `spawnIfNeeded` takes the `fcntl` record lock on `<socket>.lock` before it starts the daemon. A record
     lock belongs to the whole process, so two app threads could both hold it at once and each start a
     daemon.
   - There was a second problem: when one thread closed its descriptor, the lock dropped for every thread.
   - The fix is a static `NSLock` taken before the file lock, so threads in one process queue up first.
   - **Evidence:**
     - After run 1, nine `playhouse-daemon` processes were still alive in the VM.
     - One service's socket log (`f5a681cd…sock.log`) shows two daemons, 1912 and 1913, that started
       listening in the same second, with three spawns per app launch.
     - The losing daemon never got a connection, so it never exited (open item 2).
   - **Coverage:** `test_bridge_daemon_starts_on_demand_serves_watchers_and_exits_when_idle` now asserts
     that the daemon log holds exactly one daemon PID.
     - The CLI case starts four `status` calls at once, in separate processes.
     - The UI case launches the app, which sends several requests at once from inside one process.
     - Its contract now says "exactly once even when callers race to start it".
2. **The transcript reports when history has loaded** (`Playhouse/App/TaskConversationView.swift`).
   - Until the window's first history read finishes, the scroll view's accessibility value is
     `Loading conversation history`.
   - After that it keeps the existing `Showing latest N of M messages` value.
   - Nothing visible changes; the value tells assistive technology and tests that the history is still
     loading.
   - `openTask` and `refreshStandaloneChatSidebar` wait for it.
   - Before this, several cases read draft text, pending questions or reveal state from a transcript that
     had not loaded yet.
3. **A closed slide-up panel no longer catches clicks** (`Playhouse/App/McpServersSectionView.swift`,
   `Playhouse/App/SkillsPageView.swift`).
   - The MCP, Skills and Rules panel overlays now take hits only while a panel is open:
     `.overlay { panels.allowsHitTesting(<panel open>) }`.
   - The scheduled-tasks and skills slide-ins already used the same pattern.
   - **Symptom:** after you created an MCP server, New Server did nothing until something else re-rendered
     the page.
   - The change also stops a still-fading scrim from swallowing the next click.
   - Details are under confirmation 2.

## Failures and repairs

### Run 1 (6 failures)

1. **`test_bridge_daemon_death_fails_the_turn_and_recovers_on_next_request`**: tearDown reported
   "codex.app_server.started launched /opt/homebrew/bin/codex instead of a test fixture". This is a
   test-harness defect, exposed by #189 and #192.
   - **Cause:** after a daemon restart, every request runs the reattach scan once per data folder. The
     scan's `ConversationManager` keeps the provider clients of whichever request reached the new daemon
     first.
   - The test's `daemonProcessID` helper sent `status` without the case's provider executables. When that
     poll was the first request, the reattached turn's history read later started the real Codex CLI.
   - **Fix:** `daemonProcessID` merges `providerExecutableEnvironment` like every other CLI call.
   - tearDown now records violations before cleanup, so a failed case keeps its data directory.
   - The product side is in open item 1.
2. **`test_claude_pending_question_recovers_after_provider_process_restarts`**: test defect, exposed by
   #189.
   - **Cause:** the case killed the daemon to simulate a recovery turn dying. Since #189 the Claude process
     survives that kill and reattaches (`claude.turn.reattached`, `processAlive: true`).
   - The test also wrote `.recovery-release` and deleted it at once. The fixture polls every 20 ms and
     missed it.
   - So the question could only come back once the fixture's 30 s hold expired, after the test's 15 s
     window had closed.
   - **Fix:** both suites now kill the Claude process running the recovery turn (`claudePID` from
     `claude.turn.started`). They remove markers only after that process is gone.
3. **`test_conversation_shows_subagent_delegation`**: "/Users/admin" is not equal to the fixture's
   `primary` folder. Fixture defect, exposed by #192.
   - **Cause:** with one shared app-server, the Codex fixture's process working directory is the
     daemon's, not the thread's. The fixture reported `os.getcwd()` as the subagent command's working
     directory.
   - **Fix:** the fixture records each thread's `cwd` from `thread/start` and `thread/resume`
     (`THREAD_CWDS`, `workspace_cwd()`).
   - The CLI assertion compares against the folder as given rather than the resolved path, which matches
     what the protocol reports.
4. **`test_claude_background_agent_keeps_turn_open_until_resolved`**: test defect.
   - **Cause:** the automatic outcome-nudge turn closed "Worked for" again after the test had opened it.
   - **Fix:** wait for the turn and its nudge to settle (Waiting Response, no pause button), then expand
     the section while it reads Collapsed.
5. **`test_claude_large_image_message_reaches_idle_agent`**: "Reopening the conversation should still
   show the screenshot." Test defect.
   - **Cause:** a reopened conversation shows only the newest turn, so the earlier turn's image was off
     screen.
   - **Fix:** reveal the earlier turn before asserting the image.
6. **`test_codex_interrupted_turn_blocks_with_reason_and_can_retry`**: "Clicking the question option
   should select it."
   - The click landed while the transcript was still scrolling.
   - Clicks on question options now go through `selectQuestionOption`, which waits for a stable frame
     before clicking.
   - Temporary scroll tracing was added for this case. The failure did not recur in four later runs, and
     the tracing was removed (open item 4).

### Run 2 (27 failures): races the faster waits exposed

Between runs 1 and 2 the suite got the speed change described under "Speed". These 27 failures were all
reads or clicks that had depended on XCTest's roughly 1 s first-check delay to land after the UI settled.

| Group | Fix |
| --- | --- |
| Instant read after reopening a task: draft text, pending question, reveal state on empty history | `waitForConversationLoad()`, which waits for the history-loaded signal above |
| Click on a slide-up skills, rules or MCP panel, or a page, that was still moving or behind the fading scrim of a panel that had just closed | `openPanel(_:with:afterClosing:)` waits for a stable frame. The retry exists only for the case of reopening right after a close. |
| `accessibleLabelOrValue` read from an element that did not exist yet | It returns `""` when the element is missing, so callers can poll it |
| Image follow-up answer matched with `firstMatch`, which picked the reminder reply | Match on the exact answer label |
| Drag of the Waiting Response card, and the legacy-link glyph screenshot | `waitForStableFrame` before the action |
| Instant reads of `Claude · Opus 5.5` and of the question status after switching provider | Wait for the element, and `waitForStatus` |

A focused run of all 27 passed 25. The other two had different causes:

- **`test_codex_pending_question_recovers_after_provider_process_restarts`:** the "app-server stopped"
  banner shifted the layout under the Green option, so the click missed. Fixed by
  `selectQuestionOption(identifier:)`, which waits for a stable frame and then for the option to report
  "selected".
- **`test_task_progress_reports_clear_on_failed_turns_and_questions`** (Codex progress mid-turn): fixture
  defect.
  - While it held a turn, the fixture never answered `thread/items/list`.
  - **Cause:** Python's buffered `sys.stdin.readline()` had pulled the request line into a buffer that
    `select()` cannot see.
  - **Fix:** a `StdinLines` reader with its own buffer over the file descriptor. The new `stdin_select()`
    checks that buffer before calling `select()`, at all six places the fixture waits on stdin.

### Confirmation 1 (4 failures)

1. **`test_claude_outcome_reminder_rejects_user_questions`**: "Waiting Response" is not equal to "In
   Progress".
   - `Diagnostics.jsonl` shows the product working as designed:
     - When the question arrives, the task flips In Progress → Waiting Response (`BridgeCore.swift`,
       `onUserInput`).

   - **Fix:** `waitForStatus(taskID, "In Progress")` after the card appears. The card only appears after
     the flip, so the wait cannot pass on the In Progress from before the question.
2. **`test_claude_background_agent_keeps_turn_open_until_resolved`**: the "Worked for" disclosure was at
   y=100, under the window header (the scroll view starts at y=164). All 21 clicks hit the header.
   - **Fix:** `scrollFullyIntoView` before each click.
3. **`test_task_repository_removal_preserves_state_on_dirty_worktree`**: the new task's repository title
   read "No repository selected". The remembered selection loads after the empty conversation first
   renders.
   - **Fix:** wait for the label to become `secondary`. The failure message prints the label it last saw.
4. **`test_conversation_shows_mcp_and_dynamic_tool_activity`**: "the submitted user message must remain
   visible". This was a stale expectation that passed only when the check happened to run early.
   - Since #119, "Working for" is open while a turn runs. With four tools in flight it is taller than the
     412 pt viewport.
   - By design, the transcript then follows the live activity (`scrollToLatest` /
     `scrollToLatestUserMessage` in `TaskConversationView.swift`). The failure hierarchy had the message at
     y=-175 and the latest active row in view.
   - The original assertion only passed when it ran before the activity rows rendered.
   - **Fix:** the check now targets the regression the original message names, blank space. It passes
     when either:
     - the message is fully in the viewport, or
     - the message is above the latest active row, and that row is fully in the viewport.
   - It fails if the message is missing, or if neither is in view.
   - The shared contract sentence was rewritten to say this, identically in all three places.

All four passed in one focused run.

## Quality changes

- **Settle helpers:** `waitForConversationLoad`, `openPanel`, `selectQuestionOption(identifier:)` and
  `waitForStableFrame` replace hand-rolled waits and instant reads. Twelve raw question-option clicks now
  go through the helper, which confirms the option reports "selected".
- **`openPanel`:**
  - It clicks once and waits for the panel to settle.
  - Earlier in the round it had an `afterClosing` retry for reopening right after a close. The
    ui-verifier had already limited that retry to the 4 sites that needed it, so it could not hide a dead

  - Product change 3 removed the cause, so the retry is gone and those 4 sites now guard the fix.

- **tearDown:**
  - Provider-executable violations are recorded before cleanup, so a failing case keeps its data.
  - The provider-kill recovery paths are ordered so markers are removed after the process is gone.

## Open items

1. **The reattach manager uses an arbitrary request's provider clients.** After a daemon restart,
   `resumeReattachedRuns` runs once per data folder with the clients of whichever request arrives first.
   In production every request carries the same defaults, so there is no user impact. The fix belongs in
   `BridgeCore` by keying the clients to the reattached run.
2. **A daemon that never gets a connection has no idle exit.** The idle timer starts only after the last
   connection closes, so a daemon that loses a spawn race lives on as an orphan.
   - **The listen race (related):** `BridgeSocketListener.listen` checks for a live socket, then unlinks
     and binds. Two daemons from different processes can still interleave there. The spawn lock removes
     the in-process cause, but not this one.
3. **The Claude window shows the bridge-error banner during a reattached turn.** It reads "Couldn't reach
   the Playhouse bridge daemon" even though the turn continues after the restart.
4. **`test_codex_interrupted_turn_blocks_with_reason_and_can_retry`** had a one-off scroll miss in run 1.
   If it recurs, add scroll tracing again.
5. **`hasLoadedConversation` reflects only the first load** of a window. Later reloads keep the loaded
   value (architecture-reviewer note). That is fine for its current use.
6. **The CLI daemon-race assertion uses separate processes.** That path was already covered by the file
   lock, so only the UI case catches an in-process regression of the new `NSLock`.
7. **The Codex fixture's reattach mode** (`codex-app-server-fixture.py`, around line 807) still reports
   `os.getcwd()`.
8. **`test_claude_outcome_reminder_rejects_user_questions` "no outcome nudge" check.** It reads the
   fixture history right after the status restore, so a nudge sent later could go unseen (ui-verifier
   note). This predates the round.
9. The open items from the 11-07 report that this round did not touch still stand.
10. **WebKit GPU hangs in the Tart VM** appear even on a fresh boot: 58 events in the first 30 minutes.
    The runner guard suggested on 11-06 still applies: restart the VM when these events appear.
11. **A hung Monaco load never turns into an error** (`MonacoDiffEditor.swift`).
    - The readiness check counts attempts only after `didFinish`, and each attempt waits on
      `evaluateJavaScript`.
    - If the web content process stalls, as it did when its GPU process was killed, no callback returns.
      The overlay then shows "Starting editor" forever, with no error and no "Reload editor" button.
    - A wall-clock deadline that calls `fail(with:)` would let users recover.
12. The slide-up panel overlay (scrim, transitions and hit-test gate) is copied in three views. A shared
    modifier would stop a future copy from missing the gate (architecture-reviewer note).
13. **Start the next nightly with a full run on a quiet host.** This round's last full run was not fully green: three time-limit failures under host load, which passed when rerun alone. The round concluded without another full confirmation. If the time-limit failures come back with the host idle, profile the transcript cases. They are the ones nearest the 3-minute limit, so they show host contention first.
