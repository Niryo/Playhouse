## Product changes in this round

All four fix regressions or races that the suite caught. Users would notice each of them.

1. **Presentation atoms no longer change the view they cover** (`Playhouse/App/Plugins/Atoms/AtomViews.swift`).
   - **The defect:** #233 wrapped `AtomSidePanel` and `AtomPage`, base and overlay, in
     `.accessibilityElement(children: .contain)`. #236's `.pluginPresentation` then applies Modal, SidePanel and
     Page around the whole task conversation at all times, so the conversation sat inside those containers
     even with nothing presented. Three symptoms followed:
     - The Done task's "Follow-up changes open a fresh worktree from main" `Label` split into an Image
       labeled "Archive" and a StaticText. Both carried the hint's identifier (failure hierarchy of
       `test_done_task_accepts_follow_up_conversation`).
     - The disabled Start Implementing button's native tooltip never appeared.
     - The Stop button's element was missing for a moment while a Claude woken turn ran.
   - **The fix:** neither atom adds a container. The README's Page and SidePanel rows now say the covered
     view's accessibility tree stays untouched.
   - **Proof:** each case failed in run 1 and again in a focused rerun. All three passed with #236's app changes
     reverse-applied, and again with only the two containers removed. Ten SidePanel, Page, archive and
     plugin-presentation cases still passed without the containers, including the catalog's `group: true` base
     Stacks that the removed comment named.
2. **Unsent comments are saved where they change, not by an observer** (`TaskConversationView.swift`).
   - **The defect:** #232 put `.onChange(of: annotations) { persistPendingAnnotations() }` on the composer.
   - **The fix:**
     - `addAnnotation` saves the new comment.
     - `restoreAnnotations` saves once, only when the restored pending set differs from the saved one. That
       covers the cleanup after an interrupted clear, which the observer used to do.
     - Sending already saved explicitly.
   - **Bisect:** `test_conversation_follows_latest_streamed_messages` failed with #232 present and passed with
     #232 reversed, or with only this observer removed.
   - **Caveat:** that case later failed once without the observer, so the observer is not its whole cause. See
     change 4.
3. **The board no longer alerts on a pull-request probe for a task that has left Review**
   (`KanbanBoardView.swift`).
   - **The defect:** a probe in flight when the task moved to Done covered the board with "Pull request operation
     failed: Couldn't inspect the local head for pull request #501." The Done move had removed the worktree
     (`test_merged_task_renew_opens_fresh_worktree_and_new_pr`, screenshot).
   - **The fix:** a new `isStillInReview(id)` check is used by both error paths, the focus/appearance probe and
     the autopilot poll. It requires the task to still be in Review and every non-pending worktree path to still
     exist, because the move removes the worktrees before it saves Done.
   - **Trade-off:** a Review task whose worktree was deleted outside Playhouse now fails its probe silently
     instead of showing that alert. The reviewers accepted this.
4. **The composer cannot send before the conversation's first history load** (`TaskConversationView.swift`).
   - **The defect:** the view's `.task` awaits `reconcileLifecycleStatusOnOpen` before `loadConversation()` sets
     `isLoadingHistory`. During that wait the Send button and Return both worked. A message sent then is
     followed by the load, which resets following and pins the newest turn. If the reply had already outgrown
     the viewport, the transcript never followed it.
   - **The fix:** `isSendDisabled` and `sendMessage`'s guard both require `hasLoadedConversation`. That flag is
     set once, when the first load lands. Every other caller of `sendMessage` runs after a load.
   - **Not proven:** that this window caused the follow-latest failures. The preserved data was lost when the VM
     rebooted. Since the change, the case has passed in every run: three focused runs and the final run.

## Test changes in this round

1. **New paired case, `test_review_probe_failure_alerts_only_while_in_review`** (contract, CLI and UI;
   parity is now 203).
   - **CLI:** a failing gh makes `task pr status` fail as operation_failed with gh's own error. The Done move
     removes the worktree.
   - **UI:** a gh fixture holds each probe for about 2 seconds, then fails it. While the task is in Review the
     board raises the alert naming the error. When the task moves to Done during a held probe, no alert appears.
     Both states are screenshotted.
2. **11-10 open item 3, `test_task_pr_conflicts_detect_without_mutation`:** the case now checks the contract's
   "Fix Conflicts action still appears once the PR is linked".
   - It retries PR creation to get PR 501 and marks it conflicting.
   - It waits for the link and the stored number, triggers the board probe, and asserts
     `task-resolve-pr-conflicts-<id>` appears (and was absent before linking).
3. **11-10 open item 8, `test_codex_nudged_turn_work_stays_in_conversation`:** the old wording said the nudge
   is shown once, even after a later turn. The contract and both annotations now say:
   - fresh history shows the nudge exactly once;
   - after a later ordinary turn, the earlier nudge stays shown and the later turn's own nudge follows its
     message.

   Both suites assert each part. The CLI case gained the same ordering check the Claude case has.
4. **`test_conversation_persists_unsent_comments`:** the comment's source is now the latest turn's
   `final_answer`.
   - It used to be the first non-empty assistant message. That could be commentary folded into the collapsed
     Worked for, or a reply from an earlier turn the transcript does not render. The failure hierarchies showed
     only `item_assistant_fixture_9` and `_10`.
5. **`test_conversation_follows_latest_streamed_messages`:** the case now waits for the transcript to report
   it has loaded before sending. That matches product change 4.
6. **`test_plugin_add_mode_toggles_and_shows_placeholders`:** the case leaves the mode with `plugin mode --off`
   after opening the chat.
   - Opening the chat grows the window past the VM's 1024-pt screen, which puts the banner's Close button
     off-screen (screenshot).
   - Close is still clicked and asserted on the board, earlier in the same case.
7. **`assertDoneDrawerResting`:** when the columns are wider than the board, the helper first scrolls the board
   to its trailing end, then checks the drawer sits beside the last column.
   - #234 made the drawer an overlay with a trailing gutter "so the last column scrolls clear of it". In a
     1024-pt window the last column ends at x 1055 at scroll offset 0, under the drawer at x 1002.
   - The other resting checks run before the scroll and are unchanged.

## Open items for the next night

1. **The Stop button disappears for a moment during a Claude woken turn.** This is the last open failure, in
   `test_claude_background_agent_keeps_turn_open_until_resolved` at line 14884, the check "The woken parent's
   turn must stay active". It hit the same case in run 1 and `test_claude_settles_turn_after_consumed_wake_notification`
   in confirmation 2.
   - **Likely mechanism, not proven:** the composer shows Stop only while `isResponding` is true
     (`composerModel`, around `TaskConversationView.swift:5248`).
     - The send path sets `isResponding = false` when its send returns (around 6324), even if
       `providerTurnIsActive` still reports the woken turn running.
     - Until `watchRunningTurnIfNeeded` takes the turn over again, the composer shows Send.
   - **Next step:** capture whether the send returned at the first result (the diagnostics' `claude.turn.ended`
     against the turn's later result). Then decide whether Stop should follow `providerTurnIsActive`.
2. **Why the comment observer stopped follow-bottom is not explained** (architecture concern).
   - If the SwiftData write in `savePendingAnnotations` invalidates the transcript mid-stream, adding a comment
     while a reply streams could still interrupt following.
   - Check it with a focused run that adds a comment mid-stream.
3. **Window frames leak between cases.**
   - SwiftUI keeps `NSWindow Frame main` and other frames in the app's standard defaults
     (`com.playhouse.app.e2e.ui`). The per-case isolated preferences don't cover that domain.
   - Run 1's viewports were up to 1207 pt wide in places; the final run's were 791. The width-dependent failures
     (open-chat growth, board swipe, the drawer) follow from that.
   - Nine `playhouse.codex.completed-response-duration.<task>` keys also landed in that domain.
   - Either clear the domain's window frames in `launchApp` or launch every case at a fixed window size.
4. **On screens narrower than about 1,440 pt, opening the chat pushes trailing controls off-screen**: the
   board's 980-pt minimum plus the chat's 460 pt. The Add Plugin mode banner's Close is one of them. This is a
   usability edge for small screens.
5. **Architecture follow-ups:**
   - Route every user edit of pending comments through one saving mutator.
   - Consider one presentation host instead of three stacked presentation atoms around the conversation.
6. **Restore cleanup has no test.** Plant an already-sent comment through `task.comments.save`, reopen the task,
   and assert `pendingCommentCount` returns to 0, in both suites.
7. **The Done-hint check depends on element order.** Assert exactly one element carries
   `archived-conversation-follow-up-hint` before reading it.
8. **A full run doesn't fit in one 2-hour agent command.** The runner could gain a split or resumable mode.
   Otherwise the nightly should run on a quiet host, where the suite takes about 100 minutes.
9. **The branch has no upstream.** `run-nightly-tests-improver-skill` has no configured upstream, so this round
   committed but could not push.
10. **Still open from earlier reports:** 11-11 items 1–5, and 11-10 items 4–7, 10, 11 and 14.
