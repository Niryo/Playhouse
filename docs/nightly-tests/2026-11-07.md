## Failures and repairs

### 1. Restored plugin windows covered the board in every case (test-harness defect)

Run 1 failed every case it reached, starting with the first alphabetically. I stopped it after 8 cases.

- **Evidence:** a live VM screenshot showed two plugin windows over the board: "Fragile" and "Hello World —
  hello-world has no plugin.json". The failures read "Unable to find hit point for ScrollView
  board-columns-scroll-view" and "New Task should create and open an empty conversation". The saved window
  state lived in the guest's `~/Library/Daemon Containers/.../Saved Application State`.
- **Cause:** AppKit saves the open windows when the app quits and reopens them at the next launch. Plugin
  windows (#176) left open by an earlier session, or by the `test_plugin_*` cases within a run, reopened
  against the next case's new data directory. They showed "has no plugin.json" and covered the board.
  `clearSavedWindowFrames()` only clears `NSWindow Frame` defaults, not saved window state.
- **Fix:** `launchAppWithOpen` passes `-ApplePersistenceIgnoreState YES`, so every case starts with no
  restored windows.
- **Proof:** a focused run of 10 cases passed 10/10. It covered the first two failed cases, the three plugin
  cases, and the first case after them alphabetically. Every later run showed no restored windows.

### 2. Review-column PR controls clipped off the board (test defect; product follow-up)

Six cases failed:

- `test_done_archive_displays_existing_pull_request_link`
- `test_task_pr_create_reports_real_gh_failure` (hover changed 0 pixels)
- `test_task_done_removes_worktree_and_preserves_branch` (0 green pixels on the completion checkmark)
- `test_task_auto_pr_toggle_creates_pull_request_on_review`
- `test_task_pr_conflicts_detect_without_mutation`
- `test_task_pr_create_skips_unchanged_repositories` (clicks had no effect)

- **Evidence:** the failure screenshots show the persistent sidebar (#57, with #171's Agents info) pushing the
  three columns right. On the VM's 1024-point screen, the Review column's trailing edge sits past the board's
  visible edge, and that is where the card's PR and completion controls are. They stay in the accessibility
  tree but receive no hover or click.
- **Fix:** a new `revealOnBoard(_:)` helper scrolls the board sideways in bounded steps until the control lies
  fully inside the visible board, and asserts that it does. It is called before each such control's first
  hover, click, or pixel check (7 sites).
- **Proof:** all six cases passed in focused runs and in the final run.

**Product follow-up (architecture review CONCERN):** `ChatSidebarLayout.minimumBoardWidth` is still 980, but the
three 264-point columns plus spacing, padding, and the 185-point sidebar need about 1,069 points. At the
window's minimum width, the Review column is clipped by about 89 points. The default 1,280-point window is not
affected. See open item 2.

### 3. App-wide text queries aborted on the new scroll bar's numeric value (test defect)

Three cases failed with "Failed to get matching snapshots: Timed out while evaluating UI query":

- `test_task_token_waste_ranks_claude_items_by_size` (168 s)
- `test_task_token_waste_ranks_codex_items_by_size` (155 s)
- `test_task_pr_create_reports_real_gh_failure`, in its help-tag check

- **Evidence:**
  - A CPU profile in the VM showed the app idle (0% CPU) during the hang.
  - The app's log shows `Can't use in/contains operator with collection 0 (not a collection)`, then
    `XCTPerformOnMainRunLoop work timed out after 60.0s`.
  - The failure hierarchy has the board's new horizontal `ScrollBar` and its `ValueIndicator`, both with
    numeric `value: 0`. That scroll bar exists because of item 2.
- **Cause:** `element(containingAccessibilityText:)` and `helpTagIsShowing` matched
  `value CONTAINS[c] …` against every element. On a numeric value, that comparison raises inside the app,
  which aborts the query until XCTest gives up. An app-wide query reaches the board's scroll bar before any
  sheet, so the Token stats sheet was never searched.
- **Fix:** both helpers now use `textPredicate(containing:caseInsensitive:includeTitle:)`. It compares
  `value` only when the element type is not a numeric-valued one (scroll bar, value indicator, slider,
  progress and level indicators, check box, radio button, switch, toggle, stepper, disclosure triangle,
  splitter). The predicate short-circuits, so a numeric value is never compared as text.
- **Proof:** the token-waste cases went from 168 s and 155 s failures to 33 s and 40 s passes. The PR help-tag
  check passes.

### 5. Plugin menu choice pressed Return before the item was highlighted (flaky, test defect)

`test_plugin_failures_show_errors_and_recover` failed in run 2: after Plugins ▸ Unparsable ▸ Open, the window
never appeared.

- **Evidence:** the passing focused run and the failing full run hovered the item at identical coordinates.
  The helper then waited a fixed 400 ms before pressing Return. Under full-run load, Return arrived before the
  hover had highlighted the item.
- **Fix:** `clickMenuItem` waits until the hovered item reports `isSelected`, re-hovers once if needed, and

- **Proof:** the case passed in both later runs.

## Deliberately left alone

- **Other `value CONTAINS/BEGINSWITH` queries.** All are scoped to static texts, text views, a single element, a
  sheet, a transcript row, or a code block. None searches the whole app, and none failed. The UI reviewer
  listed them as candidates for `textPredicate` if they ever start timing out.
- **The 51 raw back-to-board clicks** that `returnToBoard()` could replace. Only one has ever been shown to
  flake, and each conversion adds about 0.4 s.
- **A prompt from an interrupted Codex turn reappears as a draft.** In the Codex interrupted case's failure
  screenshot, the retry message was "Start work that will be interrupted.Retry the interrupted task."
  (63 bytes = 36 + 27). The interrupted prompt was not in history, so the composer got it back as a draft.
  The case switches from `codex-fixture-interrupted` to `codex-fixture-ui` across a relaunch, and each fixture
  keeps its own `.history`. This may be a fixture-fidelity gap rather than a product defect. The case does not
  assert the composer there. See open item 6.
