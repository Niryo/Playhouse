# Nightly UI suite round — 2026-11-06

This round ran the visible Playhouse UI suite in Tart under `.agents/skills/nightly-tests-improver/SKILL.md`.
It started the evening of 11-05 on `master` at `3895575`, with a clean working tree and nothing staged.

## User-visible product changes

1. **A prompt that already reached the conversation is no longer returned to the composer when its
   send fails.** This applies to Claude and Codex alike.
   - Example: the provider exits after the turn has started.
   - Before (#163): the app put the text back in the composer and saved it as an unsent draft.
     After the next relaunch, the draft was prefixed to the user's next message ("Ask a
     restart-safe structured question.Follow up after private recovery.").
   - Now: the transcript keeps the delivered prompt, the composer stays empty, the error is
     shown, and no draft is saved.
   - A prompt that never reached the conversation still returns to the composer as before.
2. **The inline repository editor now shows the value that was saved, not the value that was typed.**
   - A branch-from found only on the remote is saved as its remote-tracking branch (`origin/...`).
   - After saving, the editor's branch, branch-from, and merge-target buffers are reset from the
     saved record.

## Failures and repairs

### 1. Opening a task clicked the token counter (test defect, 8 cases)

Eight cases failed inside `openTask`:

- `test_conversation_composer_rejects_blank_and_supports_live_turn_controls`
- `test_conversation_isolates_failing_claude_turn_from_parallel_send`
- `test_conversation_runs_concurrent_claude_sends_in_parallel`
- `test_conversation_serializes_concurrent_sends`
- `test_review_sync_pushes_unpushed_changes_on_completion`
- `test_task_pr_autopilot_fixes_red_pull_request_until_green`
- `test_task_store_serializes_cross_process_writes`
- `test_waiting_response_task_moves_to_review_manually`

Evidence:
- The failure screenshots show the Token stats sheet, not the task.
- #158 made the card's token counter a button. Its frame (x 441–473.5, y 262.5–287.5) contains the card's center (471.5, 282). `card.click()` lands on the center, so for any task with token usage it opened Token stats.

Fix: `openTask` now clicks the card's title (`task-title-*`). It asserts the title lies inside the visible card, and that `task-view-title` appears after the click.

### 2. Branch-from editor test written against a removed button (merge skew, then a product defect)

`test_task_repository_branch_from_fetches_remote_branch` (#162) used `save-conversation-repository-button`, which #160 removed when it redesigned the repo chips. The test now:

- saves through the per-field checkmark, `conversation-repository-branch-from-save`;
- waits for the field before editing;
- after a successful save, waits for the field to close;
- after a rejection, asserts the field stays open for correction;
- after Escape, waits for the value field to disappear.

With the test fixed, the run exposed a product defect: after saving a remote-only branch-from, the editor still showed the typed `feature` while the stored record said `origin/feature`. The fix is in `saveConversationRepository` (`TaskConversationView.swift`): the edit buffers are reset from the record that `BoardTaskManager.updateRepository` returns. This is product change 2 above.

### 3. Back-to-board click lost after a turn ends (flaky, test defect)

`test_review_pr_conflicts_probe_and_verify` clicked back-to-board in the same moment the finished turn reloaded the transcript and moved the header. The click did not register, and the case went on to look for the board's resolve button inside the task view.

The new `returnToBoard()` helper fixes this. It waits for the button to be hittable and its frame to stop moving, clicks it, and asserts `board-title` appears. The Claude isolation case uses the same helper.

### 4. Stale task-creation expectation after #163 (test defect)

`test_task_creation_persists_ordered_roots_across_fresh_connections` still expected a `task.prompt.write.*` event for the new task. Since #163, a Backlog task's prompt is saved as a draft. The case now asserts the following:

- `task.draft.write.succeeded` is recorded with status Backlog.
- `task.draft.write.started` carries the prompt's UTF-8 byte count.
- No `task.prompt.write.started` with `submitted == "true"` is recorded.

### 5. Delivered prompt restored as an unsent draft (product defect from #163)

`test_codex_pending_question_recovers_after_provider_process_restarts` failed. After the relaunch, the follow-up went out as "Ask a restart-safe structured question.Follow up after private recovery."

Evidence:
- In the case's `Diagnostics.jsonl`, right after `conversation.send.failed`, there is a 39-byte draft write. That is exactly the first prompt.
- The provider exits after the turn has started, so the send reports failure even though the prompt is already in the conversation.
- The catch branch in `sendMessage` restored the text to the composer, and `persistDraft()` saved it.

Fix: `sendMessage` records the newest message ID before its optimistic append. On a non-interrupt failure, `historyIfSendReachedConversation` reloads history and looks for the sent text as a user message after that anchor.
- If the anchor is missing, the prompt counts as not delivered, and it returns to the composer as before.
- If the prompt is found after the anchor, the reloaded history is applied and the composer stays empty.

The anchor replaced an earlier count-based check during review. The count-based check could misjudge a repeated prompt or a page-limited window.

Coverage added for both providers:
- **Codex** (`test_codex_pending_question_recovers_after_provider_process_restarts`, CLI and UI): after the failed send and after each relaunch, the prompt is in history, the composer is empty, and `hasUnsentDraft` is false.
  - The case attaches screenshots of the failed-send state and of the recovered pending question.
- **Claude** (`test_conversation_isolates_failing_claude_turn_from_parallel_send`, CLI and UI): the failing task keeps its prompt, both while open and after it is reopened from the board, with an empty composer and no unsent draft.
- The contract expectations for both cases were updated identically in all three places.

### 6. Monaco "stopped unexpectedly" in the diff view (environment defect)

`test_task_workspace_changes_group_staged_and_unstaged_diffs` showed "Monaco couldn't load this diff: the editor stopped unexpectedly."

Evidence:
- The VM's unified log has 313 `GPUProcessProxy::didBecomeUnresponsive` events during the run. Each ends in `GPUProcessCrashedTooManyTimes` and in `webViewWebContentProcessDidTerminate`.
- The first of these events in the VM's log history is at 21:01:17 UTC, five minutes into this run. Earlier rounds have none.
- Other worktrees' sessions on the same VM hit the same events.
- SwiftTerm is not the cause: its Metal renderer is excluded.

Fix: I stopped the VM under the host-wide VM lock (`scripts/with-file-lock.py /tmp/playhouse-ui-tart-playhouse-ui.lock tart stop playhouse-ui`), and the next run booted it fresh. After the restart, an 18-minute focused run showed no GPU events, the confirmation run showed one in its last 90 minutes, and the case passed both times.

No product change was made. Restarting Monaco after its WebContent process ends is left as an open item; the case's "Editor 1" check would still catch a silent reload.
