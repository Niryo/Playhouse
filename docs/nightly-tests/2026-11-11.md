## Product changes in this round

Two changes touch product code. Only the first changes what users see.

1. **A Skills page reopened while it is still sliding out reloads its catalog**
   (`Playhouse/App/TaskConversationView.swift`).
   - **Before:** if Skills was opened again during the closing slide, SwiftUI revived the closing
     `SkillsPageView` with its old identity. Its `.task` did not rerun, so the page kept showing the catalog
     it had read before.
     - In run 1 the reopened page still listed a committed skill copy that the test had just deleted.
     - `Diagnostics.jsonl` shows no `skills.list` request after the reopen.
   - **Now:** each opening increments `skillsPresentation`, and the page carries `.id(skillsPresentation)`.
     A reopen always builds a fresh page that reads the catalog.
2. **Async question options report whether they are selected** (accessibility only). Each option has
   `accessibilityValue` "selected" or "not selected", so the UI test can assert which answer the click
   chose. The visible UI is unchanged.

## Runner change

**`scripts/test-ui-tart.sh` reboots a reused VM whose GPU has restarted since boot.**

- Before reusing a running VM, the runner checks for any `.gpuRestart` report in
  `/Library/Logs/DiagnosticReports` newer than `kern.boottime`. If it finds one, it stops and restarts the
  VM under the VM lock it already holds.
- The existing artifact-share restart now uses the same `restart_vm` function.
- **Why:** the same Monaco failure has come back five times: 11-04, 11-06, 11-09, 11-10 and in this round's
  run 2. Every time a fresh boot cleared it. See failure 4 below for the evidence.
- **Verified:**
  - The focused run printed the restart message and passed.
  - After the reboot, the same check returns "reuse", so reports from before the boot don't trigger it.
  - The final run reused that VM, as it should.
- This closes 11-10 open item 12. It doesn't help when the GPU restarts during a run; see open item 2.

## Failures and fixes

### Run 1 (3 failures)

1. **`test_skills_private_create_list_convert_and_delete`: product defect.**
   - The reopened Skills page showed a stale catalog. Fixed by product change 1.
   - **Test change:** at the second reopen, the test clicks Back and then immediately clicks the Skills
     button's recorded position. It then waits for the private skill to appear unshadowed, and attaches a
     screenshot.
   - **Coverage caveat (ui-verifier requirement):** XCUITest's idle wait after a click (about 0.4 s)
     usually outlasts the slide-out. The test therefore catches a regression of this fix only when the
     reopen happens to land during the slide, and it can't force that timing on every run. A precondition
     that asserted the slide was still running was tried and failed for exactly this reason, so it was
     removed.
2. **`test_codex_async_question_queued_answer_retries`: test defect.**
   - "No" was queued instead of "Yes": the click landed while the transcript was reloading and moved the
     options.
   - **Fix:** the test now selects the option by its exact identifier through `selectQuestionOption`. That
     waits for a stable frame, scrolls the option into the conversation viewport, clicks, and asserts the
     selection.
   - The async render case now asserts "not selected" and then "selected" through product change 2.
3. **`test_codex_interrupted_turn_blocks_with_reason_and_can_retry`: test defect.**
   - The Blue option (y 124) sat above the scroll view's top edge (y 164) once the queued-message bar
     appeared, so the click missed.
   - **Fix:**
     - The new `revealInConversation` helper scrolls the option into view before clicking.
     - The test now waits for the queued bar's `steer-queued-message-<ID>` button. The bar's container is
       not an accessibility element.

### Run 2 (1 failure)

4. **`test_task_workspace_changes_group_staged_and_unstaged_diffs`: environment defect.** The diff stayed on
   "Starting editor".
   - **Evidence, VM log times in UTC:**
     - 00:47:46.36: Monaco's page finished loading (`didFinishLoadForFrame`).
     - 00:47:49.40: WebKit logged `GPUProcessProxy::didBecomeUnresponsive … terminating it`.
     - From then on, the WebContent process never answered another `evaluateJavaScript`. It was not
       terminated, and the editor still said "Starting editor" about 35 s after the click.
   - **Why the VM was degraded:**
     - It had been up 19 h 48 m, with 596 MB of swap in use.
     - Kernel `.gpuRestart` reports dated after boot already existed before the run started (12:11 and
       20:41 on 11-10).
     - More kernel GPU restarts at 23:17, 23:23 and 23:28 were followed by 139 WebKit GPU-unresponsive
       events and 27 `GPUProcessCrashedTooManyTimes`.
   - **Fix:** the runner change. On the rebooted VM the case passed in a focused run in 56.7 s, and it
     passed again in run 3.
   - The case's 5 s wait is unchanged. A longer wait would only hide the hang described in open item 3.

## Open items for the next night

1. **The native tooltip sometimes never dismisses** (`test_task_pr_create_reports_real_gh_failure`).
   Hover moves reach WindowServer, but the tooltip stays. It passed all night. If it fails again, capture
   the VM log for the window and check which view is under the final hover point.
2. **The GPU can degrade during a run.** In run 3, the kernel wrote one new `.gpuRestart`, along with one
   WebKit GPU-unresponsive event. The next run's pre-run check will reboot the VM, but a long run can still
   degrade partway. If WebKit cases fail late in a run again, consider checking between batches
   (`PLAYHOUSE_UI_BATCH_SIZE`).
3. **A hung Monaco load never turns into an error** (`MonacoDiffEditor.swift`, carried from 11-09 item 11).
   - `checkScriptReady` counts attempts only after each `evaluateJavaScript` reply. A stalled content
     process never replies, so the overlay shows "Starting editor" forever, with no "Reload editor" button.
   - A wall-clock deadline that calls `fail(with:)`, or that reloads once within the restart budget, would
     let users recover. Covering it needs a paired case that stalls the WebContent process, for example
     with `SIGSTOP`.
4. **Architecture concern:** the GUI `selectRepositories` (`TaskConversationView`, around lines 3197–3225)
   uses `BoardTaskManager.addRepositories` plus its own settings write, instead of
   `WorkspaceManager.addRepositories`. The two paths differ in turn reservation, worktree preparation and
   the paths they save.
5. **Architecture concern:** within one opening, `SkillsPageView.reload()` throws away the quick result
   whenever it already has a catalog. After a delete or move, the page shows stale entries until the
   bundled list returns.
6. **The 11-10 items still open:** 3–8, 10, 11 and 14.
