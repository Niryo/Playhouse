## Product changes in this round

One change touches product code. Users see no difference.

1. **The bridge records every GitHub CLI start** (`Playhouse/App/BridgeCore.swift`).
   - `PlayhousePullRequestService.recordStarted(_:executable:)` writes a `github.cli.started` diagnostic with
     the operation and the resolved `gh` executable.
   - It runs at the start of `findOpen`, `create`, `merge`, `isMerged` and `reviewState`.
   - **Why:** the UI suite's tearDown guard (`providerFixtureViolations`) now treats a `gh` started outside
     the fixture folders the same way as a real Codex or Claude CLI, and fails the case. The diagnostic is
     what makes this check possible. Before, a case could reach the VM's real `/opt/homebrew/bin/gh` and
     still pass.

## Failures and repairs

### Run 1 (5 failures)

1. **`test_task_pr_autopilot_fixes_red_pull_request_until_green`**: `"pr"` is not equal to `"manual"`.
   This was a stale expectation after #205.
   - **Fix:** the mode pill now expects `pr`, with a message saying every new task starts in PR mode.
2. **`test_done_archive_displays_existing_pull_request_link`**: the retry label read "PR. Create a pull
   request for the repository without a linked pull request". This was a stale expectation after #212.
   - Since #212, the button counts only the repositories that still have no PR, so a single missing PR
     reads as singular.
   - **Fix:** the test expects the singular label.
3. **`test_task_repository_default_branch_from_uses_fresh_origin`**: the task branch's upstream was `origin`
   when it should be empty. This was a test defect exposed by #205.
   - **Cause:** the task was in PR mode, so on Review the product published the branch to the fixture
     origin and set its upstream.
   - **Fix:** the case is about the task's base, so it and the two other branch-from cases set
     `task pr mode <id> manual`.
   - The default branch-from CLI case got the same change.
4. **`test_task_repository_removal_preserves_state_on_dirty_worktree`**: `NSPOSIXErrorDomain Code=35`
   (`EAGAIN`). This was a test-helper defect exposed by #205.
   - **Cause:** the product writes Review before the turn finishes. The turn still holds the task's
     conversation-turn reservation while it creates the PR the task's mode asks for. The case's next step
     tried to take that reservation and got `EAGAIN`.
   - **Fix:** `completeCurrentTaskWithFixtureAnswers` now waits for the reservation to be released when it
     expects Review. It checks the lock with `ConversationTurnLockBarrier.isHeldByAnotherProcess`, a
     `F_GETLK` probe.
   - Other expected statuses are not waited on, because autopilot's fix turn takes the same reservation
     straight after.
5. **`test_conversation_history_pages_claude_transcript_from_store`**: the case went over XCTest's
   3-minute limit.
   - **Cause:** once every message was loaded, the case still scrolled toward the first turn in dozens of
     400-point steps, and each step waited for the app to go idle.
   - **Fix:** `scrollTowardFirstTurn()` makes one 40,000-point scroll at the two points where no page is
     left to reveal. The paging assertions before those points are unchanged.
   - The case now runs in 103 to 111 s.

The gh tearDown guard (product change 1) was added after run 1, so that cases reaching a real `gh` fail
instead of passing.

### Run 2 (4 failures)

1. **`test_review_sync_pushes_unpushed_changes_on_completion`**,
   **`test_review_sync_resolves_conflicts_with_provider_or_blocks`**: "gh isMerged ran /opt/homebrew/bin/gh
   instead of the gh fixture". The new guard caught these, and they were test defects.
   - **Cause:** the daemon resolves `gh` from each request's own environment
     (`PlayhouseProcessEnvironment.requestEnvironment`). The app had the gh fixture, but the test's own
     `task pr sync` CLI calls did not, so the daemon ran the VM's real `gh` for those requests.
   - **Fix:** every `task pr sync` call in both cases passes `extraEnvironment: ghEnvironment`.
2. **`test_task_pr_conflicts_detect_without_mutation`**: "gh findOpen ran /opt/homebrew/bin/gh". This was a
   test defect, and both suites had a check that passed for the wrong reason.
   - **UI case:** it expected PR creation to fail, and that failure came from the real, signed-out `gh`.
     - It now launches with a gh fixture that fails the first create.
     - It requires the alert text "GitHub CLI couldn't complete the request. fixture GitHub create failure".
     - It reads the fixture's create log and asserts exactly one failed create, run in the task worktree.
   - **CLI case:** its create had always failed with "Codex CLI wasn't found", before it ever reached `gh`,
     because PR creation asks the task's provider for the PR text first.
     - It now uses the Codex fixture that ran its turn and the same failing gh fixture.
     - It asserts the same message and the same worktree.
3. **`test_default_parent_settings_read_write_clear_and_validation`**: "Suggestions from the previous parent
   should be replaced." This was a test defect: the check passed or failed depending on timing.
   - **Cause:** the alternate parent sits inside the first parent (`suggested-parent/alternate-parent`), and
     `RepositoryScanner` recurses the whole tree. So `alternate` was already listed before the parent
     changed, and the old check could run before the refresh had finished.
   - **Fix:** the case waits until the first parent's `primary` is gone, then asserts `alternate` is listed.

A focused run of all four passed. Times: settings 79.0 s, sync push 39.6 s, sync conflict 28.4 s, PR
conflicts 20.9 s.

### Run 3 (2 failures)

1. **`test_codex_nudged_turn_work_stays_in_conversation`**: "The later ordinary turn should finish with an
   answer." This was a fixture defect, and the case had been passing on a race.
   - **Cause:** the nudged-work fixture creates a `.nudged-steer-pause` marker so the nudge turn waits for a
     steer, for up to 60 s.
     - The marker was never removed after use.
     - The later ordinary turn also ended without an outcome, so it got its own nudge. That nudge found the
       old marker and waited the full 60 s.
     - The app-server then exited (`os._exit(3)`), `codex.turn.wait_failed` was logged with "Private
       conversation recovery turn failed.", and the task moved to Blocked.
   - Earlier runs passed only when the test's 60 s wait happened to win: the UI case took 73 to 77 s and
     the CLI case about 61 s every time.
   - **Fix:** the fixture removes the pause and ready markers after each steer, so every pause gets one
     steer.
   - Both suites now also assert that after the later turn the task is in Review, not Blocked.
2. **`test_task_workspace_changes_group_staged_and_unstaged_diffs`**: the diff editor stayed on "Starting
   editor". This was an environment defect.
   - The VM's unified log shows Playhouse killing the WebKit GPU process (SIGKILL) 3 to 5 s after each
     launch, again and again, so web content loads stalled. `gpuRestart` reports had piled up in
     `/Library/Logs/DiagnosticReports` overnight.
   - The failure reproduced in a focused run.
   - After `tart stop playhouse-ui`, with the VM lock confirmed free, the case passed in 55.8 s on a fresh
     boot.
   - **Fix:** none in code. The case's 5 s wait is still correct (see "Left alone deliberately").

## Quality changes

- **The suite can no longer reach a real `gh`.** The tearDown guard and product change 1 together enforce
  this. Its failure message says what to do: give the case the gh fixture, or set a task that is not about
  pull requests to Manual mode.
- **Two PR-failure checks no longer pass for the wrong reason.**
  - The UI conflicts case had depended on the real `gh` being signed out.
  - The CLI case had failed on a missing Codex CLI.
  - Both now prove that `gh pr create` ran once, in the task worktree.
- **The Codex nudged case checks the task's outcome:** both suites assert Review after the later turn, so
  the old marker leak would now fail the case at once instead of costing 60 s.
- **The Review reservation wait** lives in one helper, `completeCurrentTaskWithFixtureAnswers`, instead of
  in each caller.

## Left alone deliberately

- **The diff editor's 5 s "Starting editor" wait.** The run 3 failure came from the VM's degraded WebKit
  GPU, and the case passed on a fresh boot. A longer wait would hide a real hung Monaco load (11-09 open
  item 11).
- **The slowest transcript and plugin cases:** see "Speed".
