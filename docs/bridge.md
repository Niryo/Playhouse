# Playhouse CLI and bridge daemon

The `playhouse-cli` executable is bundled at `Playhouse.app/Contents/MacOS/playhouse-cli`, and the bridge daemon at `Playhouse.app/Contents/MacOS/playhouse-daemon`, both beside the GUI executable. The CLI's distinct filename avoids macOS case-insensitive name collisions. Both executables live flat in `Contents/MacOS` (not in their own bundle) so that `Bundle.main` resolution, for either of them, finds the same app `Info.plist` the GUI process itself has — the daemon and the CLI share the app's identity automatically, with no separate bundle of their own. The CLI connects to the daemon over a Unix domain socket, starting it on demand (lock-guarded against a concurrent caller doing the same) if nothing is listening yet; the daemon exits on its own once idle (no open connections and no turn in flight) rather than staying resident. Run the CLI through `scripts/playhouse.sh`, which builds the app if needed. CLI calls and app instances do not acquire the UI test lock; worktree profiles isolate app identity, socket path, data stores, logs, and build paths.

The daemon accepts a versioned, length-prefixed JSON request over its socket, streams zero or more event frames while the turn runs, then returns exactly one versioned JSON response frame. The CLI derives the daemon's socket path from the same app identity it shares via `Bundle.main`, so linked worktree app profiles each get their own daemon and socket. Errors include a stable code and a readable message; the CLI exits nonzero for failed operations.

For example:

```sh
./scripts/playhouse.sh task create --title "Update parser" --prompt "Update the parser to ..." --repo /work/parser --root /work/fixtures
./scripts/playhouse.sh task move 33F746B9-3E5E-4D84-890A-257BDB01B66A Review
./scripts/playhouse.sh conversation send 33F746B9-3E5E-4D84-890A-257BDB01B66A --message "Inspect the parser and summarize its error handling."
```

Repository worktrees are created under `task-worktrees` in the app data directory (`~/Library/Application Support/Playhouse/task-worktrees` for the primary profile), so removing that folder removes them too; worktrees made before this keep their recorded paths; if the requested branch already has a worktree, Playhouse reuses its current path. By default, the branch name is derived from the task title. `--branch` and `--branch-from` values are keyed to the repository path as `<repo-path>=<value>`. Branch creation uses `master`, or the detected default branch if `master` is absent. Moving a task to Done removes clean worktree directories while leaving their branches; a dirty worktree blocks the status change. Folder-only tasks store their roots directly.

The selected worktrees and context folders define task context and the initial working directory; they do not restrict the provider's full-access sandbox configuration.

New conversations start with the picker closed and the composer focused. Playhouse applies the saved ordered repository selection when available. An empty repository selection is valid: the conversation may be standalone, and the composer remains enabled without a working-folder warning. For an empty-root task, Codex starts in the user's home folder while its task repository roots remain empty, so the configured repository root is not used as a task working directory.

The configured repository root folder (the parent that contains the user's repositories) must be set to an available directory before a conversation can be sent. The GUI disables send and offers a setup button while it is missing or unavailable. The CLI/daemon conversation-send operation also rejects the turn with `settings_required`, so callers cannot bypass the requirement.

The thread developer instructions are sent to the Codex app-server when a conversation thread starts or resumes. They distinguish source repository paths from active task worktree paths and require repository edits to use the worktree. On a new task, Playhouse starts the user's conversation immediately and runs a separate fast Codex assessment process in parallel. The primary agent is instructed to avoid repository edits while that assessment is pending. Only if a mismatch is likely does Playhouse call its repository-list operation and steer the primary turn to request user confirmation. If the first turn ends before the assessment can steer it, Playhouse surfaces a notice with the result and asks the user to continue in a follow-up. Playhouse displays mismatch confirmation as a dialog and blocking AI questions in a modal sheet.

Codex must not scan or enumerate folders under the configured repository root to discover repositories. When it needs another repository or a refreshed list, it must use `workspace repos list`, which returns `{ "root": "...", "repositories": ["..."] }`; it may recommend only paths from that response. If no listed repository clearly matches, it should ask the user rather than searching or guessing. The task repository add APIs are available in the thread instructions. They can run while the main conversation is active, prepare an editable managed worktree immediately, update the saved repository selection, and return the repository-to-worktree mapping. The active turn's original `cwd` does not change mid-turn, so after adding a repository Codex must use the returned worktree path for edits in that repository; subsequent turns automatically receive the updated workspace roots. Repository replacement validates/adds the requested repositories before removing old ones. If an old managed worktree is dirty or removal fails, the operation reports failure and preserves both contexts. Codex can ask a blocking question using the app-server's user-input request; Playhouse shows it in a modal sheet.

## Skills

Claude Code and Codex read the same `SKILL.md` format from different folders. Codex reads the open Agent Skills layout (`.agents/skills` in the working repository, `~/.agents/skills`, and its own `$CODEX_HOME/skills`); Claude Code reads `.claude/skills` in each workspace folder and its configuration directory's `skills`. Playhouse treats all of them as one gallery (`SkillCatalogManager` in `Playhouse/App/SkillCatalog.swift`), so a skill added anywhere works with both providers in Playhouse sessions, and new skills are written to the Agent Skills layout.

At each turn's launch, Playhouse bridges the skills a provider would not otherwise see, without writing to repositories or either provider's settings:

- Claude Code gets `--add-dir` for a Playhouse-owned wrapper under `<data>/skill-bridge/claude/<key>` whose `.claude/skills` holds one symlink per bridged skill, and `--settings '{"skillOverrides":{...:"off"}}'` for disabled skills.
- Codex shares one app-server across tasks, so it gets `skills/extraRoots/set` with every task's wrapper under `<data>/skill-bridge/codex/<key>`, and each thread starts with a `config.skills.config` that disables other tasks' bridged skills and the task's disabled skills by path. A `/skill-name` in the message is also sent to Codex as a structured `skill` input, since Codex has no slash commands. A thread that is already loaded keeps the skill configuration it started with.

Wrappers are content addressed and never changed once written, so concurrent launches can share them; ones unused for 14 days are removed. A skill named twice in one scope with different contents is reported as a conflict and not bridged; each provider keeps its own copy. `skills link` writes a real symlink (relative inside a repository) for use outside Playhouse. Requests from a test bundle (`.e2e.` builds) with an isolated data directory read skills from `<data>/skills-home`, so tests never see the host's skills; development worktree builds read the user's real skills.

## Rules

Rules are the instruction files an agent follows on every turn. Codex reads `AGENTS.override.md` or `AGENTS.md` in each folder from the Git root down to its working directory (32 KiB in total) and one in `$CODEX_HOME`; Claude Code reads `CLAUDE.md`, `.claude/CLAUDE.md`, `CLAUDE.local.md` and `.claude/rules/**/*.md` (optionally scoped by `paths` frontmatter) in its working directory, its configuration directory's `CLAUDE.md` and `rules`, the managed `CLAUDE.md`, and a repository's `AGENTS.md` only when no `CLAUDE.md` is beside it. Codex's own `~/.codex/rules/*.rules` files are command-approval policies, not instructions, and are not listed. `RuleCatalogManager` in `Playhouse/App/RuleCatalog.swift` lists all of these as one set, and new global rules go in `~/.agents/AGENTS.md`, which neither CLI reads on its own, as `~/.agents/skills` does for skills.

At each turn's launch, Playhouse shares the rules a provider would not otherwise read, without writing to repositories or either provider's settings:

- Claude Code gets the text of those rules (such as `~/.agents/AGENTS.md`, Codex's global `AGENTS.md`, and the other task repositories' files) appended to its system prompt, with `@path` imports expanded. Its `--settings` adds `claudeMdExcludes` for turned-off files it reads itself and, when the working repository has both `AGENTS.md` and a `CLAUDE.md`, sets the built-in AGENTS.md plugin to `claude-md-and-agents-md` so it reads both.
- Codex gets the same kind of text (such as `CLAUDE.md`, `.claude/rules`, and Claude's global files) in the thread's developer instructions, after the task instructions, leaving out files it already reads. When the shared rules change, the next send resumes the thread with the new instructions.

A path-scoped rule is shared as a pointer naming its globs and file. A turned-off rule is no longer shared, but Codex still reads its own native files (the working repository's `AGENTS.md` and its global one), and the record's `alwaysOnFor` says so. `rules link` writes real symlinks for use outside Playhouse (relative inside a repository).

## MCP servers

Claude Code reads `mcpServers` in its state file (`~/.claude.json`, or `.claude.json` in `$CLAUDE_CONFIG_DIR`), the working directory's `.mcp.json` (once approved), the managed `managed-mcp.json`, plugins and claude.ai connectors. Codex reads `[mcp_servers.<name>]` in `$CODEX_HOME/config.toml` and a trusted project's `.codex/config.toml`. `McpCatalogManager` in `Playhouse/App/McpCatalog.swift` lists the file-backed ones as one set: definitions with the same name in one scope are one server, and a server whose definitions differ is a conflict that is passed to no one and can be fixed by an agent. `CodexConfigTOML` edits only a server's own `[mcp_servers.<name>]` tables and keeps every other line of `config.toml`; servers written inline are listed but left to the user. Claude's state file is written under its `<file>.lock` folder lock.

At each turn's launch, Playhouse passes each provider the servers it does not start itself, without writing to either provider's configuration:

- Claude Code gets `--mcp-config` with Codex's own servers, the working repository's `.codex/config.toml` servers and the other task repositories' `.mcp.json` servers, and `--settings` with `enabledMcpjsonServers` and `disabledMcpjsonServers` for the working repository's `.mcp.json`. A server with a Codex `cwd` is not passed to Claude, which has no equivalent.
- Codex gets the thread's `mcp_servers` config, which it merges server by server over its own `config.toml`: Claude Code's and the repositories' servers translated to Codex keys, and `enabled = false` for its own servers turned off on the page. SSE servers and `${…}` references Codex can't express stay Claude-only. A change resumes the thread on its next turn.

Claude Code has no per-run switch for a single server from its own configuration, so turning one off applies to Codex only and the record's `alwaysOnFor` says so; deleting it removes it for both. `-c mcp_servers={}` never disabled Codex's own servers (Codex merges tables), so it is no longer passed. `mcp status` asks Claude Code (`mcp_status`, with the task's MCP bridge) and Codex (`mcpServerStatus/list`) and reports `needsSignIn` for `needs-auth` and `notLoggedIn`; Playhouse doesn't sign in for the user.

## Plugins

A plugin is a JavaScript file that builds UI with React and `createElement` from native atoms; a custom React renderer in JavaScriptCore sends its commits to Swift as mutation ops, and SwiftUI draws the resulting node tree. See `Playhouse/App/Plugins/README.md` for the atoms, the op protocol and how to write one. The app menu's Plugins menu opens the Plugin Catalog, which renders every atom and the task item through the renderer. The plugin core (`Playhouse/App/Plugins/Core`, Foundation and JavaScriptCore only) is compiled into the app and the daemon, where `plugin render` runs a plugin headlessly through the same runtime and node tree.

## Shared implementation

The GUI and the daemon both compile `BoardTaskManager`, `WorkspaceManager`, `WorkspaceSettingsManager`, and `ConversationManager` from `Playhouse/App/BridgeCore.swift`; the daemon dispatches operations via `PlayhouseBridgeRuntime.perform`, unchanged by the transport underneath it. `PlayhouseStore` opens the same application-support SwiftData store in both. In debug bridge tests, each request can supply an isolated store and defaults suite; release builds ignore those overrides.

### Who owns what

The daemon is the only process that owns provider state: every Codex app-server, every Claude Code process, every running turn, the turn reservation, and the queued-follow-up dispatcher. The window runs no provider. Its conversation operations (`send`, `steer`, `stop`, answering questions, history, goals, models, title generation, pull-request creation, archive search, task deletion) go through `RemoteConversationManager`, which sends the same bridge commands the CLI sends, so a window and a command-line call always reach the same turn and there is no cross-process steering or interrupt fallback. Operations that only read or write Playhouse's own store (queued follow-ups, model and effort choices, task edits and the board's `@Query`) stay in the window, because the SwiftData store is safe across processes and the window needs those answers synchronously while it renders.

The window follows the daemon's turn state through `conversation runtime --watch` (`conversation.runtime.subscribe`): a long-lived request that streams `runtime_state` snapshots (active, interruptible, and interrupted conversations, pending questions, and Codex goal revisions). `ConversationRuntimeModel` mirrors the latest snapshot for the views and re-subscribes, starting a fresh daemon if needed, when the connection drops. `conversation runtime` returns one snapshot.

A turn's live updates reach whoever started it. Any other caller follows them with `conversation watch <task-id>` (`conversation.events.subscribe`): it streams a `watching` event and then the same update events a send streams (text deltas, progress, activities, questions, `completed`) for whatever turn the task is running, whether a window, the CLI or a schedule sent it, or the daemon reattached it after a restart, and it ends when that turn ends. On a task with no running turn it returns `{"watched": false}` at once. A window opens one whenever its task has a running turn it didn't send.

Quitting the window does not stop a turn; it only stops watching. The daemon keeps any running turn alive and exits `PLAYHOUSE_BRIDGE_IDLE_GRACE_SECONDS` (10 by default) after its last connection closes with no request in flight.

### Agents outlive the daemon

The provider agents keep running when the daemon dies (a crash, SIGKILL, or a rebuild that replaces it), and the next daemon of the same service carries their turns on. Every agent is started by `AgentRunHost` (`Playhouse/App/AgentRunHost.swift`) in its own session and process group, with only its three standard descriptors open, so neither the daemon's signals nor its bridge socket reach it. Each one is recorded in an atomically written manifest that names the service, the process and its start time (a pid alone can be reused), written before the spawn so a daemon killed right after starting an agent still leaves a record.

- **Codex** runs one shared `codex app-server --listen unix://…` per shared-client key (executable, Codex home, data folder and service name), always with `features.goals=true`. A window's requests and the CLI's use the same client and so the same server: Codex serializes its sign-in token refresh only within one process and lets a thread be open in only one process, so two servers on one Codex home could sign the user out (`refresh_token_reused`) or block each other on a thread. The Codex home in the key is resolved, so a caller that sets `CODEX_HOME` to the default `~/.codex` shares the server of one that doesn't set it. Account and usage reads, sign-in and sign-out go through the same server; an account or usage read it doesn't answer within `PLAYHOUSE_CODEX_ACCOUNT_READ_TIMEOUT_SECONDS` (30 by default) fails without stopping the server, and the last known account and usage stay. Its manifest, log and socket live in `<data>/codex-runs/<key>.{json,log,sock}`; a socket path longer than macOS allows moves to `/tmp/playhouse-codex/<uid>/`. `CodexSocketConnection` speaks WebSocket over the Unix socket (Network.framework's WebSocket stack can't run over a Unix endpoint). Short-lived helper clients (titles, page classification) keep a stdio child that ends with them.
- What a window does differently from the CLI on that server is per request: a window's requests carry `__guiRuntime`, so its history reads and Goal sets follow the thread's Goal turns (`goal.observedThreadIDs` and the goal revisions in `runtime_state`) and own the action handler, while a CLI Goal or history call only performs its request. A history read, from either, never resumes a thread under a running send or a turn Codex runs on its own, such as a Goal's work turn (which counts as active and interruptible whoever set the Goal), and a CLI Goal call never stops the server. A server started under the earlier key, which also held two goal flags, is reattached by a client of its own only to follow a turn it still runs, then retired as soon as it is idle; until then two servers briefly run on that Codex home.
- **Claude Code** speaks only stdio, so each turn's `claude -p` gets file-backed stdio in `<data>/provider-runs/<session>-<run>/`: `agent.in` is a FIFO the process itself also holds open, so it never reads end of input while no daemon is writing. Claude Code's runtime waits for kqueue to report its input readable, and on macOS kqueue never reports a FIFO readable while a blocking write of more than the FIFO holds is pending, so a large line (a message with a screenshot) written in one blocking write would never arrive. The daemon therefore writes each line off the main actor, in order, through a non-blocking descriptor in 4 KiB chunks (`AgentInputWriter`); a line that makes no progress for 30 seconds fails that send, stops the agent, and ends its turn with that reason instead of freezing every conversation. `agent.out` and `agent.err` are append-only files the daemon tails. `run.json` records how far the log was handled (`consumedOffset`), which control requests were answered, which questions are still pending, and the highest request number sent. A reply is written before the offset that covers its request is committed, so a daemon that dies in between answers again (Claude Code ignores a repeated reply) and one that dies after never does. Claude Code exits on a malformed input line, so a daemon killed in the middle of writing one loses that turn; the run marks such writes, and the next daemon settles the turn as interrupted.

A turn's active marker in `conversation-turn-locks/` records the service running it. On its first request for a data folder (a window, any CLI call, or a scheduled `schedule tick`), a daemon goes back to every turn of its own service whose marker outlived its daemon, before it answers anything:

1. It stops any process whose standard streams point into the run folders but that no manifest (of any service) accounts for, except one writing into a spawn still being recorded.
2. A Codex turn whose server still runs is reconnected: `thread/resume` with `excludeTurns` re-sends any approval or question that is still pending, and `thread/turns/list` and `thread/items/list` (which carry the real item IDs) say whether the turn is still running or finished in the meantime. Codex doesn't replay notifications missed while nothing was connected, so the server's state is the source of truth.
3. A Claude turn whose run still exists is replayed from its log without side effects up to the committed offset, which rebuilds its result, activities, background tasks and pending question, and the rest of the log is handled live. A reattached runner numbers its control requests past the previous daemon's, so a late reply to an old request can't answer a new one.
4. A reattached turn holds its task's turn reservation and reports through the same callbacks and the same finish (outcome, status, auto-PR on Review, queued follow-ups) as a turn sent normally, and `BridgeBackgroundWork` keeps the daemon up until it ends. Steering, Stop (Codex `turn/interrupt`; for Claude an interrupt, then the run is stopped by its verified identity) and `conversation watch` work as for any turn. A window whose send failed because its daemon went away reconciles the task and follows the reattached turn instead of reporting an error.
5. A turn whose agent is gone, or that has nothing to reattach, becomes Waiting Response with "The agent stopped while Playhouse was restarting. Your conversation is saved; send a follow-up to continue." A saved question stays answerable.

Only one daemon of a service can serve at a time, and each shared Codex server also has an exclusive ownership lock beside its manifest that the kernel releases when its holder dies, so a successor never connects to a server while its predecessor still exits. Another service on the same data folder (a test suite's private daemon, for instance) never reattaches, sweeps or stops this service's agents.

A shared Codex server stops by itself after `PLAYHOUSE_CODEX_SERVER_IDLE_SECONDS` (600 by default) with no turn, question, operation or active Goal, and right away once idle when it was started by another Codex version or with other flags. Before an idle daemon exits it stops its idle servers and any Claude run left after its turn. A server with an active Goal keeps running with nothing connected: the Goal keeps working until one of its turns needs an approval or a question answered, and then waits for the next daemon to reconnect and receive that request (verified with `codex-cli 0.162.1`: pending requests stay pending and the thread stays loaded for at least 10 minutes with no client).

The daemon and CLI are built by `scripts/build-bridge.sh` during the app target's Xcode build phase. The CLI name is deliberately distinct from `Playhouse` because the default macOS filesystem is case-insensitive. Keeping both executables in `Contents/MacOS` also lets them resolve the same app identity via `Bundle.main` with no separate bundle of their own.

## Verification

`Playhouse/BridgeTests/BridgeTestContracts.json` defines the shared case IDs and their expectations. Each Python CLI case and Swift UI case carries an annotation that must exactly match the shared entry. `scripts/check-test-parity.py` fails if either suite has a missing, extra, duplicate, or mismatched case. The fast verifier reviews assertions in both implementations to confirm each pair covers the same behavior.

`scripts/test-e2e.sh` builds or reuses a content- and toolchain-matched app bundle per worktree and runs the Python CLI/daemon cases against its embedded executable and daemon. Each invocation has fresh committed Git fixtures and isolated app data. It does not take `.e2e.lock`, so it can overlap UI sessions and other worktrees. Build creation uses a per-worktree cache lock; callers of the exact same cached build use a build-local `.bridge-run.lock` to protect shared daemon diagnostics routing. Documentation (`docs/`, `README.md`) and agent configuration (`.agents/`, `.codex/`) do not invalidate that build cache; app resources, project settings, and build scripts remain fingerprinted. Every source edit produces a new build, so after each build or reuse the helper prunes the cache (`scripts/e2e_build_cache.py`, checked by `scripts/check-e2e-build-cache.py`): it removes a build only when it has been idle for two hours (`PLAYHOUSE_E2E_BUILD_CACHE_MAX_IDLE_SECONDS`, never below ten minutes), is superseded by a more recently used build of the same worktree or belongs to a worktree that no longer exists, and neither its `.bridge-run.lock` nor its worktree's cache lock is held. Each live worktree keeps at least its most recent build. Fixture/log artifacts are retained in the printed directory. The runner reports static-check, build, fixture, case, and total durations; build output distinguishes cache reuse from misses, and each case reports elapsed seconds. Lock output identifies the holder PID/worktree and queue wait. A contended lock is a blocking kernel wait, not a retry loop: the waiter reports contention immediately, refreshes its waiting message every 20 seconds, and an interval timer enforces `PLAYHOUSE_UI_LOCK_TIMEOUT_SECONDS` (exit 124). `PLAYHOUSE_LOCK_WAIT_REPORT_SECONDS` overrides the reporting interval and exists for the lock tests. Runtime-discovered case names must exactly match the shared contract, with no missing, skipped, or incomplete cases. The headless suite does not start an XCTest runner or UI automation.

`scripts/test-ui-tart.sh` visibly launches the real app in the Tart VM and runs all matching cases through the user interface. Pass `--case <case-id>` once or more to run a focused subset. `scripts/test-ui.sh` on the host automatically hands off to the VM runner; the underlying UI suite runs only in the guest. It uses real persistence and the same fixture, and does not need Codex sign-in. Routine verification assigns the CLI/daemon suite to one task verifier and runs the read-only UI coverage and architecture reviews in parallel against the same fingerprint. `scripts/test-full-e2e.sh` remains available for deliberate full CLI-plus-UI runs, with its UI stage in the VM. New cases should each cover one logical behavior: small related expectations can extend an existing case, while independent behavior or distinct failure paths need a paired case in both suites.

Each headless run creates a fixture under its temporary artifact directory with clean committed Git repositories, nested-repository and symlink cases, and a marker checked before replacement. Test stores and preferences are unique per case, and persistence is checked using new CLI processes and daemon connections. The Xcode bridge adapter still uses `/tmp/playhouse-bridge-workspaces` when invoked directly.

The UI suite requires XCTest UI automation in a logged-in macOS desktop session. The Cirrus Xcode VM image preconfigures Automation Mode without requiring user authentication, but Xcode Helper may still need Accessibility permission. If XCTest reports a timeout while enabling automation, rerun the same case with `scripts/test-ui-tart.sh --show-vm --case <case-id>`. The runner pauses after boot and before the test, so you can enable Xcode Helper under **System Settings > Privacy & Security > Accessibility** in the guest, then press Return to continue. This option requires an interactive terminal. The CLI-only suite remains headless for the usual development loop.

To run UI tests, first run `scripts/setup-ui-tart-vm.sh`, then use `scripts/test-ui-tart.sh [--vm <name>] [--show-vm] [--case <case-id>]`. The setup script creates the default VM from `ghcr.io/cirruslabs/macos-tahoe-xcode:26.5` with 6 CPUs and 12 GB memory; it requires at least 110 GiB free in Tart storage while cloning. After a fresh clone it deletes the cached OCI image and slims the guest by removing components the macOS UI suite does not use (simulator runtimes, Flutter, the Android SDK, Kiro CLI, and caches), which shrinks the host disk image by about 50 GB; `--slim` reruns that step on an existing VM. Setup holds the same host-wide VM lock as the test runner. This image includes Xcode 26.5, auto-login, Automation Mode configuration, and the Tart guest agent. The test runner starts the stopped VM with a shared artifact directory mounted, copies the checkout through it into guest-local storage, and runs the existing UI suite there. The VM-local copy is fixed for the run, so host edits made during testing do not affect it. Build products, fixtures, and app data remain in the guest during the run; test logs and `.xcresult` bundles are copied to `/tmp/playhouse-ui-tart-artifacts/<run-id>/`, then the per-run guest snapshot is removed. The artifact mount resolves to the same path for every checkout and per-run artifacts are namespaced by run ID, while the guest source snapshot is a fixed shared path, so a kept-alive VM carries no checkout-specific state and any run holding the VM lock may reuse it. The runner keeps the VM running for the next run unless `--stop-vm-after-run` is passed. Use `--show-vm` to open the display and configure Accessibility before the test starts. UI test execution on the regular host is blocked by the `test-ui.sh` handoff.

The live provider integration suite is opt-in because it requires an authenticated host provider CLI: Claude Code (the default) or Codex with access to the pinned Luna model. Run it with `PLAYHOUSE_RUN_LIVE_INTEGRATION=1 ./scripts/test-live-integration.sh [--provider claude|codex|all] [--scenario <name>] [--skip-ui]`. Shared scenarios run against the selected provider: a plan turn, then an edit turn in two disposable Git roots with command output and diff checks, a resumed turn, and a full history reload; steering an active turn; stopping an active turn from another process; concurrent automatic-branch claims; and a `/skill` turn whose skill lives only in the other provider's layout, so it can reach the provider only through Playhouse's skill bridge. Claude-only scenarios cover the question round trip and the capability report; the Codex-only scenario covers the pinned model. `--provider all` also runs a Claude → Codex → Claude handoff and checks the mixed transcript's ordering and provider boundaries. Set `PLAYHOUSE_LIVE_KEEP_WORKSPACE=1` to keep the disposable workspace for inspection. `scripts/test-codex-integration.sh` is kept as a wrapper for `--provider codex`. The live UI cases are handed off to Tart and require the provider CLI and a separate login in the guest. For an interactive guest login, run `scripts/test-ui-tart.sh --show-vm --live-provider claude --case test_conversation_composer_rejects_blank_and_supports_live_turn_controls` (`--live-codex` is an alias for `--live-provider codex`).
