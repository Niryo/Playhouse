# Playhouse agent instructions

These rules govern development work in this repository. They describe the development process; they are not features of the Playhouse app.

Whenever you need to read Swift source, use the `swift-nav` skill in `.agents/skills/swift-nav` (mirrored in `.claude/skills/swift-nav`) to locate the relevant structure and read only the needed symbol or range. Start with `outline`, use `show` instead of guessing offsets, and use `refs` instead of repeated greps. Do not read an entire Swift file into context when a symbol-level read will answer the question; if the tool fails or surrounding context is essential, use a narrow range around the relevant code.

## Git write operations

- Do not run Git commands that change the working tree, index, refs, or repository history unless the user explicitly authorizes the specific operation in the current conversation.
- Git operations performed by test runners in isolated temporary fixture repositories and their VM-local test snapshots are authorized; they do not require separate permission. This exception does not apply to the task worktree or any user repository.
- This includes `git add`, `commit`, `push`, `pull`, `stash`, `restore`, `reset`, `checkout`, `switch`, `clean`, `merge`, `rebase`, `cherry-pick`, branch or tag creation/deletion, and worktree creation/removal.
- A request to implement, edit, or review code is not permission to run a Git write command. Read-only commands such as `git status`, `git diff`, and `git log` are allowed.
- Explicitly invoking `$full-ui-verification` authorizes that skill to stage and commit only changes made for its verification and repair work, then push that commit to the current branch's configured upstream. It does not authorize including unrelated or pre-existing staged changes; if those prevent a scoped commit, finish verification and report the commit/push blocker.
- Explicitly invoking `$nightly-tests-improver` (`.agents/skills/nightly-tests-improver/SKILL.md`) authorizes that skill, in the same path-scoped way, to stage, commit, and push the changes of its improvement round once its confirmation UI run is green. It likewise never includes pre-existing staged changes.

## App operations through the bridge

- Use `scripts/playhouse.sh` for semantic Playhouse actions and state reads. It builds the app-bundled CLI when needed and sends versioned JSON requests to the bridge daemon (`playhouse-daemon`, bundled beside the CLI in `Contents/MacOS`) over its Unix domain socket, starting the daemon on demand, without opening a window. The "CLI/XPC" suite name used below is historical; the bridge no longer uses XPC.
- Implement product operations in the shared managers in `Playhouse/Core/Bridge/BridgeCore.swift`; GUI actions and CLI/daemon commands must call the same manager logic. Add a CLI operation and real bridge assertion for each new semantic product capability. Declare every CLI command once in `Playhouse/Core/Bridge/CLICommandCatalog.swift`, with its usage, a one-line description and the agent audiences that may use it: the parser refuses undeclared commands, `help` prints the declarations, and agent instructions in `Playhouse/Core/Providers/CodexTaskInstructions.swift` point agents at `help --for <audience>` instead of listing commands, so never copy command usage into those instructions. Window focus, open sheets, and current selection are transient presentation state and are outside the bridge API.

## Module layout

- Code lives in four layers, and dependencies only flow down: the macOS app target (`Playhouse/App`) → PlayhouseViews (`Playhouse/Views`, composites) → PlayhouseAtoms (`Playhouse/Atoms`) → PlayhouseUI (`Playhouse/UI`) → PlayhouseCore (`Playhouse/Core`). The packages are declared in `Playhouse/Package.swift`; the daemon and CLI build from PlayhouseCore. See `docs/linux-port-readiness.md`.
- PlayhouseCore is Foundation only (plus GRDB and Observation). Guard a platform framework with `#if canImport(...)`, call the C library only through `POSIX` (`Core/Platform/POSIX.swift`), and reach clipboard, files and URLs, cursors, windows, alerts and the login item only through `Platform.services`.
- Atoms and composites never `import SwiftUI` or AppKit: they use PlayhouseUI's `PH…` names and shims, name icons with `PHIcon`, and reach AppKit views (text editing, terminal, Monaco diff) only through `NativeViews.factory`. Persist through the GRDB model store (`Core/Storage/ModelStore.swift`), never SwiftData; observe with `@Observable`, never ObservableObject or Combine.
- Composites (everything in `Playhouse/Views`, and the app's ordinary UI: the Plugins menu, the terminal panel's chrome, the updater's settings and release notes) are composed of atoms and styled only through atom props: no raw `PHText`/`PHHStack`/`PHVStack`/`PHButton`/shapes/controls and no styling modifiers (`.font`, `.padding`, `.frame`, `.background`, `.foregroundStyle`, …). Compose a reusable piece as a Swift helper that builds atoms; when a style is missing add a prop to the existing atom, and add a new atom only for a behavior, event or platform capability no composition can express. `scripts/check-atom-composites.py` enforces this, with a short allowlist for the native exceptions; see "Composites" in `Playhouse/Core/Plugins/README.md`.
- `scripts/check-module-boundaries.py` and `scripts/check-atom-composites.py` enforce these rules; they run as the app's first build phase, in `scripts/test-e2e.sh` and in the Linux CI workflow, and `scripts/test-linux-core.sh` builds PlayhouseCore and PlayhouseUI and runs the core tests on Linux in Docker. Run both after changing Core or UI.

## Plugins

- Keep the plugin core (`Playhouse/Core/Plugins`) free of SwiftUI, AppKit and app-target types; like the rest of PlayhouseCore it uses only Foundation-level modules and Observation, and reaches JavaScriptCore only through `ScriptEngine` and is also compiled into the daemon for `plugin render`.
- Plugins compose only atoms; composites (the task item, the Agents info section, the Token Stats modal, the Skills page's header and gallery, the task header's repository chips and their Add repository picker, the conversation composer's box, the board's Done archive) are native SwiftUI built from the same atom views and are never exposed to JavaScript. Add an atom only when a native composite needs it, with its props struct, view, registry entry and a Plugin Catalog page; see `Playhouse/Core/Plugins/README.md`.
- Prefer truly atomic atoms. An atom should do one thing: lay out, draw a surface (background, border, shape), show content, or take input. Before adding an atom or a prop, check whether existing smaller atoms or props on them can compose it; if they can, compose them or add the missing primitive capability (for example a background on `Stack`) instead of a new combined atom.
- A composite atom (an atom equivalent to a composition of smaller atoms, such as a decorated container) is allowed as a convenience shortcut when the composition is very common or awkward to repeat. Every capability of a composite atom must also be reachable through the atoms it is made of, which stay exposed to plugins, so nothing a composite does is available only through it. Implement the composite's view from those atom views rather than a second implementation, document in its catalog page and the README atom table which atoms it is shorthand for, and keep its catalog page alongside theirs.
- Playhouse must never install skills, instructions, hooks or config into the user's home or repositories (`~/.claude`, `~/.agents`, `~/.codex`, a repository's `.claude/`). Agent guidance Playhouse provides is injected at runtime only, through launch flags, thread configuration or developer instructions.

## AI provider parity

- For every new feature or behavior change involving an AI provider, assess both Claude and Codex, even when the request or edited code names only one. Implement the feature for both wherever the relevant capability exists. Record each provider's implementation path and explain any difference; an existing one-provider implementation is not proof that the other provider is inapplicable.
- For behavior owned by Playhouse, such as client-side presentation, persistence, or workflow orchestration, prefer shared logic that works for both providers. Trace the behavior from UI and CLI entry through state, persistence, and provider dispatch; document why provider selection cannot change the asserted outcome. When that evidence proves the path is provider agnostic, use one representative provider in the paired CLI/UI case and do not add duplicate provider cases. Existing general provider integration coverage may establish that both providers reach the shared path. A shared view, matching case names, or a provider-neutral label alone is not proof.
- For behavior that depends on a provider's API or protocol, such as plan mode, inspect the capabilities and integration paths of both providers. Cover each applicable provider path with assertions that would fail if that provider regressed. Separate provider-specific cases when the protocols, results, or failure/resume paths differ; shared CLI/UI case naming and expectation parity still apply to every case.
- A new feature intentionally limited to one provider requires the user's explicit permission in the current conversation before implementation or approval, even when the other provider appears not to support it (for example, Codex goal mode). Present the concrete provider capability evidence, the proposed scope and user-visible behavior, and the resulting test plan when requesting permission. Do not infer permission from a one-provider request, an existing one-provider feature, or an unsupported-provider claim without evidence. If permission is absent, do not approve the one-provider feature.

## Verification scope

- Classify the current task's changed files before invoking verification. Source files include application code, test code, and executable scripts (for example Swift, Python, and shell). Documentation, agent/skill instructions, configuration, contracts/data, and assets alone are non-source changes. If no source files changed, skip tests, builds, parity gates, and all static reviewer agents; report verification as not applicable. This exemption takes precedence over the routine verification requirements below. Mixed changes that include source files use the source-change gate. An explicit user request to run tests or reviews still applies.

- The task verifier reviews only the current task's unstaged working-tree changes. Use read-only `git status --short` and `git diff` to identify that scope; include relevant untracked files as unstaged. Exclude staged-only files and staged hunks from the review. For a partially staged file, assess the unstaged delta only; staged content may be consulted as context but is not approved by the verifier.
- For every product behavior change or bug fix, add or extend a focused assertion in the headless CLI/XPC suite and the matching visible UI case. For small fixes, extend the existing logical case; for independent behavior or failure paths, create a new case in both suites. Exercise the real GRDB model store and real filesystem/settings dependencies. Cover success, validation/failure, and the highest-risk persistence or resume path. Simulated provider behavior in test fixtures is allowed under the provider fixture policy below; other mocks, stubs, fakes, or simulated implementations remain restricted.
- For provider-related changes, the task verifier checks the Claude/Codex implementation paths and CLI/XPC assertions, the UI verifier checks visible coverage and whether one representative case suffices, and the architecture reviewer checks shared ownership and provider-specific boundaries. Each reviewer must distinguish representative test coverage of a proven shared feature from a feature limited to one provider. Require separate provider cases only for behavior whose provider integration, result, error, or resume path can differ. Each reviewer must report why a provider is inapplicable when claiming an exception and verify that any one-provider design has the explicit permission required above.
- The bridge test harness must create deterministic local Git repository fixtures outside the repository (use `/tmp`), commit their baseline files, isolate app data, and verify its ownership marker before replacing or removing a fixture. Default tests must not depend on Codex or Claude Code sign-in. Live provider turns belong in `scripts/test-live-integration.sh` (Claude by default, `--provider codex|opencode|all`, where `all` runs Claude and Codex and the handoff between them) and must use the real installed Claude Code CLI, Codex CLI/app-server or OpenCode CLI. `scripts/test-opencode-scripted.sh` runs the real installed `opencode` against a local scripted model (`scripts/fixtures/opencode-model-server.py`), so it checks the OpenCode release on the machine with no account or tokens.
- Keep the headless CLI/XPC suite and visible app UI suite in exact named-case and shared-expectation parity. `Playhouse/BridgeTests/BridgeTestContracts.json` defines each case ID and expectation; both test implementations must carry the same annotation. `scripts/check-test-parity.py` must reject missing, extra, duplicate, or mismatched cases and expectations. The runtime CLI suite must execute exactly the contract's case IDs. Any new CLI test case requires the same named UI case and expectation, and vice versa. The verifier must review the assertions and UI actions to confirm that the pair exercises the same behavior, not just matching annotations.
- Run `scripts/test-e2e.sh` for the fast headless CLI/XPC suite. With no prior failures, run the full suite once. If a case fails, fix it and rerun only that case with `scripts/test-e2e.sh --case <case-id>`; after every failed case is green, run the full suite once as final confirmation. Focused runs must still validate that discovered CLI cases exactly match the shared contract, and must execute each requested case exactly once with no skip or incomplete result. The full suite must execute every contract case with no skipped test, failure, or incomplete result. Tests must launch the app-bundled CLI and reach the real persistence layer through the bridge daemon.
- UI tests must always execute in the Tart macOS VM, never on the regular host. Use `scripts/test-ui-tart.sh --case <case-id>` for the focused cases a task needs; `scripts/test-ui-tart.sh` with no `--case` is the full suite, which tasks must not run (see the rule on relevant UI cases below). Host invocations of `scripts/test-ui.sh` automatically hand off to the VM runner; inside the VM-local snapshot, that script executes XCTest. `scripts/test-full-e2e.sh` checks parity, runs the full CLI/XPC suite, then runs UI tests in Tart. Both suites use real app persistence, committed Git fixtures, and isolated per-case app data; they do not require Codex sign-in.
- The main agent is the sole runtime CLI/XPC owner. After the static review barrier is satisfied, it follows `.agents/skills/code-review/SKILL.md` and runs the suite, focused retries, and any required final confirmation directly. Do not delegate runtime execution to `task_verifier` or another subagent. Static reviewers do not build or run runtime workflows. The main agent may run cheap parity/static checks during source implementation; never run competing suites.
- All UI test runs share the single Tart VM `playhouse-ui`. Never create additional VMs: do not `tart clone`/`tart create` per task, worktree, skill, or experiment, and do not point `--vm` or `PLAYHOUSE_UI_TART_VM` at a different VM. If the shared VM is broken beyond what `--reset-vm-state` fixes, stop it, `tart delete playhouse-ui`, and recreate it with `scripts/setup-ui-tart-vm.sh`. Concurrent runs queue on the shared VM lock rather than spawning another VM.
- `scripts/test-ui.sh` runs every paired visible UI case for a deliberate full end-to-end run. Use `scripts/test-ui.sh --case <case-id>` to run one or more focused cases. `scripts/test-full-e2e.sh` checks parity and runs the full CLI/XPC suite first, then the full UI suite. Both suites use real app persistence, committed Git fixtures, and isolated per-case app data; they do not require Codex sign-in.
- When `scripts/run.sh` changes, the UI coverage reviewer checks that the paired UI case covers its restart behavior. Execute that case only through the on-demand full UI verification workflow.
- Never run the full UI suite (`scripts/test-ui-tart.sh` or `scripts/test-ui.sh` with no `--case`, or `scripts/test-full-e2e.sh`) as part of a task. It takes about an hour and is reserved for `$full-ui-verification` or an explicit user request for it. For every task, run only the UI cases that are relevant to the change, each with `--case <case-id>`: (1) the UI cases the task added or edited, (2) the UI cases whose paired CLI case the task edited, and (3) the UI cases that exercise the code, views, or helpers the task touched (find them by searching `Playhouse/PlayhouseUITests/PlayhouseUITests.swift` for the identifiers, labels, commands, and fixtures the change affects). When a shared helper changes (for example `runCLI` or `createTaskFixture`), run the cases that depend on it and that the change could plausibly affect, not every case that calls it. Cases that fail while you do this get fixed and rerun; unrelated cases that you did not select are not run. State in the final response which UI cases were run and why each is relevant.
- Routine task verification does not run the full UI suite. After the static review barrier and required CLI/XPC checks pass, the main verifier runs only the paired UI case(s) that directly showcase the changed visible behavior, in Tart via `scripts/test-ui-tart.sh --case <case-id>`. Keep this to the smallest set of cases and runs that demonstrates the feature; do not run unrelated cases or the full suite. The matching UI test must attach a screenshot for each meaningful state needed to review the behavior. Export those attachments from the returned `.xcresult` bundle with `xcrun xcresulttool export attachments`, select the showcase images, and publish each with the task-specific Playhouse CLI `conversation present-image <task-id> --image <path> [--caption <caption>]`. Showcase screenshots must be clearly readable at their published size: capture them with the UI tests' `attachScreenshot(named:)`, which crops to the app's windows and popovers at native pixel density, never publish a whole-desktop capture, and add an element-level capture (`element.screenshot()`) when the changed UI is small within its window. Before publishing, open each exported image and confirm the changed UI and its text are legible; if they are not, fix the capture and rerun the case instead of publishing it. If the change cannot be meaningfully shown in the UI (for example, a performance-only improvement), skip this showcase phase and state the concrete reason in the final conversation response. The task verifier and UI coverage reviewer remain read-only static reviewers; the main agent owns the focused runtime run, screenshot extraction, and publishing. Full UI execution remains on demand through `$full-ui-verification`.
- State which unstaged changes were reviewed, which app workflows were exercised, and whether screenshots applied. If direct app interaction or relevant artifact checks cannot be completed, reject with the specific gap.

## App verification, E2E coordination, and mocks

- Headless `scripts/test-e2e.sh` must not acquire or be wrapped in the shared `.e2e.lock`. Each invocation has fresh committed Git fixtures and app data; builds are content- and toolchain-matched per worktree. Build creation uses a per-worktree cache lock. Runs using the exact same cached build serialize on its `.bridge-run.lock` because its bridge daemon identity, socket, and diagnostics routing are shared. Different worktrees/builds and UI sessions may run concurrently.
- Serialize visible UI test runs through the repository-root `.e2e.lock`; the UI runners acquire it for the full VM session. Ordinary `scripts/playhouse.sh` calls, live provider integration, direct app launches, and screenshots do not use this lock. Lock diagnostics report holder PID/worktree and queue wait; stale file contents alone do not mean the lock is held. Every lock here is an advisory `flock` released by the kernel when the holding process exits, including on a hard kill, so a leftover lock file is never by itself a reason to delete a lock or stop another run.
- Run the long suites (`scripts/test-ui-tart.sh`, `scripts/test-full-e2e.sh`, and full `scripts/test-e2e.sh` runs) in the background and act on the completion notification instead of blocking a foreground call. A foreground call spends the whole turn parked on a contended lock wait. Waiting for the lock is correct; occupying a turn to do it is not. `scripts/test-ui-tart.sh` defaults `PLAYHOUSE_UI_LOCK_TIMEOUT_SECONDS` to 120 and applies it separately to the `.e2e.lock` wait and the VM lock wait (so up to about 240 seconds in total), so a run queued behind a full UI suite exits 124 instead of waiting it out; raise that value when you intend to queue rather than fail fast, and treat exit 124 as "the VM was busy", not as a test failure.
- A Tart VM left running between invocations carries no checkout-specific state: nothing bound into it or recorded about it derives from the host checkout path or the login session. Any run that holds the host-wide VM lock (`/tmp/playhouse-ui-tart-<vm>.lock`, which serializes every run against that VM, including across separate clones) may reuse whatever VM is already running, regardless of which worktree started it. Before reusing it, the runner checks that the guest can see this run's artifact directory; a VM booted by an older runner or with a different `PLAYHOUSE_UI_TART_ARTIFACTS` fails that check and is restarted under the lock. Do not reintroduce an ownership marker for the VM. The guest's `SourceSnapshot` path is deliberately fixed and shared rather than per-run, because `scripts/test-ui.sh` keys the guest's reusable Xcode DerivedData off it; its ownership marker guards an `rm -rf` and is not a checkout identity.
- The routine UI coverage reviewer does not open the app. Direct app sessions and screenshots do not use the UI-test lock. Distinct worktree app profiles allow app instances from different worktrees to run alongside one another, with separate app and bridge daemon identities, sockets, data stores, logs, and build paths.
- Bridge tests and verifier actions must use the actual app-bundled CLI, bridge daemon, and real persistence. The default suite must not silently skip local product behavior; live provider operations are isolated in the separately documented opt-in suite.
- Provider fixture policy: agents may add or extend simulated provider behavior in test fixtures without asking for user permission. Fixtures may simulate provider responses and protocol events while tests exercise Playhouse's real managers, CLI/XPC, persistence, and filesystem/settings dependencies. This permission applies to both Claude and Codex fixtures and does not require signed-in providers or paid live turns.
- For other mocks, stubs, fakes, or simulated implementations, first explain the dependency and why it cannot be exercised directly, then ask the user for explicit permission. Do not add them until permission is given.
- An isolated test data directory is acceptable when it still exercises the app's real persistence implementation.
- Bridge tests should cover every semantic product capability and relevant empty, validation, and failure states. Keep each named case focused on one logical behavior or contract. Split cases when they cover independent capabilities, separate workflows, or distinct failure behavior, and when a long case makes it hard to tell which behavior failed. Do not combine task lifecycle, settings, repository discovery, and conversation behavior into one large scenario just to reduce setup or runtime.
- For a small bug fix or added expectation that belongs to the same behavior and fixture setup, extend the relevant existing case; do not create a new end-to-end case just to assert one closely related detail. Use a separate case for an independently meaningful behavior or failure path. Avoid both one-assertion test proliferation and monster cases; optimize for clear names, fast diagnosis, and complete capability coverage rather than a target test count.
- Keep shared setup in helpers, but give each case isolated app data and a fresh named behavior. Report the inner bridge case names and count in addition to the Xcode wrapper count, so a single Xcode adapter test cannot obscure how much behavior the suite covers. Coding integration coverage must inspect real fixture files, streamed events, command output, changed-file activity, and diffs on initial and resumed turns.

## Task verification gate

- The static reviewers are defined for both providers: Codex loads `.codex/agents/*.toml` (`task_verifier`, `ui_verifier`, `architecture_reviewer`) and Claude Code loads `.claude/agents/*.md` (`task-verifier`, `ui-verifier`, `architecture-reviewer`). They carry the same instructions; when you change one, update the other in the same change.
- Whether a failure is new is irrelevant. Do not exclude, tolerate, or report a failing test as "pre-existing", "unrelated", or "flaky" and move on, and do not spend a run proving it also fails on a clean checkout. If a test that runs in this task's gates fails, diagnose the cause and fix it: the product when it is a real regression (for example a leaked process, a hidden message), the test when its expectation is stale or wrong, or the test's robustness when the environment makes it intermittent. A gate is green only when every test it runs passes; a task is not complete or ready for Review with a known failing test.
- Persist through completion. Do not stop after a failed test, verifier rejection, or partial implementation while actionable work remains. Treat failures as findings to fix, then rerun the required gates and repeat until they approve.
- UI E2E repair tasks use a failure-first order. When the task is to make existing UI cases green, the main agent runs the affected cases in Tart, repairs and reruns failures until all affected cases pass, then runs the full UI suite to green, but only when the user's request is explicitly to repair or confirm the whole UI suite (otherwise rerun only the relevant cases). Do not start static reviewer agents before that UI verification is green. Afterward, run the applicable static reviews before declaring completion. If a review requires a source or test change, rerun the affected UI cases and full UI suite before repeating the affected reviews. This exception changes only the ordering; it does not waive the static review requirements for source changes.
- Any task that changes source code must go through the full verification process in this file: static reviews, the required CLI/XPC runs, and the focused showcase run when it applies. A build that does not compile, a step skipped, or a gate not yet green means the task is not done. Never report the task outcome as `completed` (which moves it to Review) until every required step has passed. If a step cannot pass and you can still work on it, keep working in the current turn; there is no outcome for unfinished work. If it needs the user's input or decision, report `waiting-response`. If an external blocker stops all progress, move the task to Blocked and state the blocker.
- Do not hand unfinished implementation or verification work back to the user when it can be continued in the repository. If a genuine external blocker prevents further progress, exhaust the available alternatives first and report the exact blocker and the specific input or state needed to proceed.
- For tasks that change source files, use two verification phases, except for the UI E2E repair ordering above. Phase 1 is static review: after implementation is ready, start the applicable `task_verifier` (explicitly in `static` phase), `ui_verifier`, and `architecture_reviewer` in parallel. Supply the same unstaged change fingerprint, task context, and exact paired UI case IDs. The task verifier owns requirements, CLI assertions, parity, and mock checks; the UI reviewer owns visible test actions/assertions and checks screenshot attachments for showcaseable states; the architecture reviewer owns design and responsibility boundaries. No reviewer builds or runs runtime tests in this phase.
- Resolve static findings before runtime verification. The static barrier requires task and UI `APPROVED`, plus architecture `APPROVED` or a documented `CONCERN`. These are static approvals, not evidence of runtime success. Repair findings and rerun only affected reviews in parallel; retain other approvals only with a recorded explanation that their relevant inputs are unchanged. Record each review's relevant files and dependencies so a new overall fingerprint alone does not force unrelated reviews to repeat.
- Phase 2 is runtime verification: the main agent checks the static approvals and approved fingerprint, then runs the required CLI/XPC checks itself using `.agents/skills/code-review/SKILL.md`. Do not resume or spawn a subagent to execute tests. If the first full run is green, it is also final confirmation: do not run another full suite.
- For runtime failures, the main agent repairs the issue and owns subsequent test execution; static reviewers remain read-only. Reopen affected static reviews before testing the repair, then run only failed cases and cases affected by the repair. Once these are green, run one final full suite. Stop after that passes unless relevant inputs change. If a build/setup failure prevents any case from executing, repair it, refresh affected static approvals, and retry the full suite; do not invent a case ID.
- Keep the reviewed tree stable during runtime verification. Compare relevant implementation, test, contract, and runner inputs at start/end; record and discard stale runtime evidence if those inputs changed, obtain affected static approvals, and restart the required runtime phase. Documentation-only changes do not invalidate behavioral evidence. Never retain evidence across relevant changes merely to save time.
- The `ui_verifier` is a read-only coverage review. It must not run UI tests or directly interact with the app. It inspects the changed behavior and paired UI test actions/assertions, judges whether the test would detect the relevant regression, and reports missing or weak coverage with concrete findings. For showcaseable changes, it also checks that the focused case attaches screenshots for each meaningful state. The implementation agent repairs any findings and reruns affected static reviews before the required CLI checks and focused showcase run.
- If the UI coverage review finds missing expectations, add or extend the matching CLI assertion and paired UI test, update the shared contract when needed, and improve the static coverage check that missed it. Do not treat the UI coverage review as a replacement for CLI coverage.
- Keep `scripts/test-full-e2e.sh` for deliberate full-suite verification. Run the full UI suite on demand with `$full-ui-verification`; that skill repairs failures, confirms the final full UI suite is green, then commits and pushes its scoped changes.
- A source-change task is complete when task and UI static reviewers report `APPROVED`, architecture returns `APPROVED` or a documented `CONCERN`, and the main agent has passing required CLI/XPC evidence plus the focused showcase run and published screenshot(s) when the change is showcaseable. Non-source-only tasks need none of these gates. If the task/UI verifier rejects or the architecture reviewer rejects, address findings and repeat the affected static reviews before runtime checks. Keep a per-task verification ledger with the unstaged change fingerprint, phase (static/runtime/showcase), review input dependencies and retained approvals, CLI cases, focused UI case IDs, screenshot states and published artifacts (or the reason showcase was skipped), coverage findings, architecture review, pass/fail, and duration; retain passes only while their relevant implementation and test inputs are unchanged.
