# StationAI agent instructions

These rules govern development work in this repository. They describe the development process; they are not features of the StationAI app.

## Git write operations

- Do not run Git commands that change the working tree, index, refs, or repository history unless the user explicitly authorizes the specific operation in the current conversation.
- This includes `git add`, `commit`, `push`, `pull`, `stash`, `restore`, `reset`, `checkout`, `switch`, `clean`, `merge`, `rebase`, `cherry-pick`, branch or tag creation/deletion, and worktree creation/removal.
- A request to implement, edit, or review code is not permission to run a Git write command. Read-only commands such as `git status`, `git diff`, and `git log` are allowed.
- Explicitly invoking `$full-ui-verification` authorizes that skill to stage and commit only changes made for its verification and repair work, then push that commit to the current branch's configured upstream. It does not authorize including unrelated or pre-existing staged changes; if those prevent a scoped commit, finish verification and report the commit/push blocker.

## App operations through the bridge

- Use `scripts/stationai.sh` for semantic StationAI actions and state reads. It builds the app-bundled CLI when needed and sends versioned JSON requests through the private XPC service without opening a window.
- Implement product operations in the shared managers in `StationAI/App/BridgeCore.swift`; GUI actions and XPC commands must call the same manager logic. Add a CLI operation and real bridge assertion for each new semantic product capability. Window focus, open sheets, and current selection are transient presentation state and are outside the bridge API.

## Verification scope

- The task verifier reviews only the current task's unstaged working-tree changes. Use read-only `git status --short` and `git diff` to identify that scope; include relevant untracked files as unstaged. Exclude staged-only files and staged hunks from the review. For a partially staged file, assess the unstaged delta only; staged content may be consulted as context but is not approved by the verifier.
- For every product behavior change or bug fix, add or extend a focused assertion in the headless CLI/XPC suite and the matching visible UI case. For small fixes, extend the existing logical case; for independent behavior or failure paths, create a new case in both suites. Exercise real SwiftData and real filesystem/settings dependencies. Cover success, validation/failure, and the highest-risk persistence or resume path. Do not add mocks, stubs, fakes, or simulated implementations.
- The bridge test harness must create deterministic local Git repository fixtures outside the repository (use `/tmp`), commit their baseline files, isolate app data, and verify its ownership marker before replacing or removing a fixture. Default tests must not depend on Codex sign-in. Live Codex turns belong in `scripts/test-codex-integration.sh` and must use the real installed Codex CLI/app-server.
- Keep the headless CLI/XPC suite and visible app UI suite in exact named-case and shared-expectation parity. `StationAI/BridgeTests/BridgeTestContracts.json` defines each case ID and expectation; both test implementations must carry the same annotation. `scripts/check-test-parity.py` must reject missing, extra, duplicate, or mismatched cases and expectations. The runtime CLI suite must execute exactly the contract's case IDs. Any new CLI test case requires the same named UI case and expectation, and vice versa. The verifier must review the assertions and UI actions to confirm that the pair exercises the same behavior, not just matching annotations.
- Run `scripts/test-e2e.sh` for the fast headless CLI/XPC suite. With no prior failures, run the full suite once. If a case fails, fix it and rerun only that case with `scripts/test-e2e.sh --case <case-id>`; after every failed case is green, run the full suite once as final confirmation. Focused runs must still validate that discovered CLI cases exactly match the shared contract, and must execute each requested case exactly once with no skip or incomplete result. The full suite must execute every contract case with no skipped test, failure, or incomplete result. Tests must launch the app-bundled CLI and cross XPC into the real persistence layer.
- `scripts/test-ui.sh` runs every paired visible UI case for a deliberate full end-to-end run. Use `scripts/test-ui.sh --case <case-id>` to run one or more focused cases. `scripts/test-full-e2e.sh` checks parity and runs the full CLI/XPC suite first, then the full UI suite. Both suites use real app persistence, committed Git fixtures, and isolated per-case app data; they do not require Codex sign-in.
- When `scripts/run.sh` changes, the UI coverage reviewer checks that the paired UI case covers its restart behavior. Execute that case only through the on-demand full UI verification workflow.
- Routine task verification does not run UI tests or directly interact with the app. The UI verifier reviews the changed behavior against the paired visible UI test, checks that the test's actions and assertions would detect regressions, and identifies any missing UI coverage. Full UI execution is on demand through `$full-ui-verification`.
- For documentation, process, or verifier-configuration-only changes that cannot affect app behavior, validate the changed artifacts; if UI test runner behavior changed, run a focused headless CLI case where applicable and review the runner selection/result-enforcement logic. Screenshots are not part of routine verification.
- State which unstaged changes were reviewed, which app workflows were exercised, and whether screenshots applied. If direct app interaction or relevant artifact checks cannot be completed, reject with the specific gap.

## App verification, E2E coordination, and mocks

- Serialize all app verification sessions through the same repository-root `.e2e.lock`. Developer-initiated suites use `scripts/test-e2e.sh`, `scripts/test-ui.sh`, or `scripts/test-full-e2e.sh`; custom E2E test commands use `scripts/with-e2e-lock.sh -- <command> [args...]`. The OS-managed lock waits 20 seconds between retries while another run holds it.
- Test scripts acquire the shared repository-root `.e2e.lock` for app verification. The routine UI coverage reviewer does not open the app; any on-demand direct app session or screenshot must hold the same lock from launch through app shutdown. Do not wrap `scripts/run.sh` alone, because it exits while the app remains open and releases the lock too early.
- Bridge tests and verifier actions must use the actual app-bundled CLI, private XPC service, and real persistence. The default suite must not silently skip local product behavior; live Codex operations are isolated in the separately documented opt-in suite.
- Do not add mocks, stubs, fakes, or simulated implementations. If a test genuinely requires a mock, first explain the dependency and why it cannot be exercised directly, then ask the user for explicit permission. Do not add it until permission is given.
- An isolated test data directory is acceptable when it still exercises the app's real persistence implementation.
- Bridge tests should cover every semantic product capability and relevant empty, validation, and failure states. Keep each named case focused on one logical behavior or contract. Split cases when they cover independent capabilities, separate workflows, or distinct failure behavior, and when a long case makes it hard to tell which behavior failed. Do not combine task lifecycle, settings, repository discovery, and conversation behavior into one large scenario just to reduce setup or runtime.
- For a small bug fix or added expectation that belongs to the same behavior and fixture setup, extend the relevant existing case; do not create a new end-to-end case just to assert one closely related detail. Use a separate case for an independently meaningful behavior or failure path. Avoid both one-assertion test proliferation and monster cases; optimize for clear names, fast diagnosis, and complete capability coverage rather than a target test count.
- Keep shared setup in helpers, but give each case isolated app data and a fresh named behavior. Report the inner bridge case names and count in addition to the Xcode wrapper count, so a single Xcode adapter test cannot obscure how much behavior the suite covers. Coding integration coverage must inspect real fixture files, streamed events, command output, changed-file activity, and diffs on initial and resumed turns.

## Task verification gate

- Persist through completion. Do not stop after a failed test, verifier rejection, or partial implementation while actionable work remains. Treat failures as findings to fix, then rerun the required gates and repeat until they approve.
- Do not hand unfinished implementation or verification work back to the user when it can be continued in the repository. If a genuine external blocker prevents further progress, exhaust the available alternatives first and report the exact blocker and the specific input or state needed to proceed.
- After every implementation task, start the applicable `task_verifier`, `ui_verifier`, and `architecture_reviewer` agents in parallel once the implementation is ready for review. Give them the same unstaged change fingerprint and task context. Supply the UI verifier with the exact paired UI case IDs identified from the task diff. The task verifier runs the fast CLI/XPC suite and static/parity checks; the UI verifier independently reviews visible test coverage; the architecture reviewer reviews implementation changes for architectural fit. The UI review does not need to wait for CLI results because it assesses test coverage, not runtime success.
- Wait for all applicable reviews before deciding the task. The task verifier and UI verifier must both report `APPROVED`; the architecture reviewer must report `APPROVED` or a `CONCERN` documented as a follow-up risk. Resolve any `REJECTED` finding before calling the task complete. If a review leads to changes, rerun the affected reviews in parallel against the new unstaged fingerprint; do not retain a pass when relevant implementation, test, or contract inputs changed. This keeps the three reviews independent while ensuring the final decision covers the same version.
- The `ui_verifier` is a read-only coverage review. It must not run UI tests or directly interact with the app. It inspects the changed behavior and paired UI test actions/assertions, judges whether the test would detect the relevant regression, and reports missing or weak coverage with concrete findings. The implementation agent repairs any findings and reruns the affected fast CLI checks and review; no UI rerun is part of routine verification.
- If the UI coverage review finds missing expectations, add or extend the matching CLI assertion and paired UI test, update the shared contract when needed, and improve the fast-verification flow that missed it. Do not treat the UI coverage review as a replacement for CLI coverage.
- Keep `scripts/test-full-e2e.sh` for deliberate full-suite verification. Run the full UI suite on demand with `$full-ui-verification`; that skill repairs failures, confirms the final full UI suite is green, then commits and pushes its scoped changes.
- The task is complete when the fast CLI verifier and read-only UI coverage verifier both report `APPROVED`, and the architecture reviewer has returned `APPROVED` or any `CONCERN` has been documented as a follow-up risk. If the task/UI verifier rejects or the architecture reviewer rejects, address findings and rerun relevant fast CLI checks and reviews. Keep a per-task verification ledger with the unstaged change fingerprint, CLI cases, coverage findings, architecture review, pass/fail, and duration; retain passes only while their relevant implementation and test inputs are unchanged. Do not run focused or full UI tests during routine task verification.

## Post-task workflow analysis

- After completing each task, invoke the `workflow_optimizer` agent defined in `.codex/agents/workflow-optimizer.toml`, scoped only to that task. Provide the task identifier/title and any task-specific progress timeline or verification ledger that is not present in the conversation. The agent analyzes the current task conversation and evidence, then updates the aggregate `workflow-improvements.md` only with supported, actionable, non-duplicate ideas. It must report measured versus estimated durations and telemetry gaps; it must not invent timing or skip required verification to reduce duration.
